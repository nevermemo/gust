# wgpu runtime

Consume compiled shader artifacts plus explicit binding/layout metadata; keep syn internals out of the runtime. Match the repository's pinned wgpu API and features.

1. Record adapter name, device type, backend, requested features/limits and shader hash. A missing adapter is unavailable execution, not a passing kernel.
2. Validate shader and pipeline, bind exactly the declared ABI, dispatch rounded-up workgroups, copy to staging, wait for mapping and compare readback.
3. Test partial groups, empty input and invalid host lengths. Propagate validation, device, mapping and comparison errors.
4. Do not substitute CPU execution or a different shader when reporting GPU success.
5. Native readback futures never wake themselves: wgpu runs the `map_async` callback inside a device poll, so `read_typed_buffer_async` completes only while something polls the device. The blocking wrappers (`read_typed_buffer`, `GpuVec::to_vec`, the `_timed` and one-shot functions) therefore call `poll(Wait)` first and then wait for the mapping's own completion, bounded (`completion::blocking`: a park-based wait on the future or `recv_timeout` on the callback's channel, 30 s, then `Error::Map`); one poll followed by one check is a race, because another thread's device poll runs every finished submission's callbacks and can collect this one's after this thread's `poll(Wait)` returned (`tests/concurrency.rs`). Awaiting the future on a native executor that sleeps until woken hangs.
6. The `wasm32` surface (browser, `webgpu` feature enabled only for wasm32) has no blocking and no clocks: `new_async`, buffers, `submit`, the typed `dispatch` and `read_typed_buffer_async` exist; the blocking readbacks, the `_timed` and one-shot `dispatch_f32`/`dispatch_u32` functions, the four blocking `dispatch_*` helpers of `HeadlessDevice`, the `graph` module and `pool_read` are `cfg(not(target_arch = "wasm32"))`. There `WgpuJob::status` is `Pending` until `on_submitted_work_done` runs, and `wait`, `wait_timeout` and every `dispatch` built on them return `Error::WouldBlock` after submitting (D131), so synchronise with an awaited readback. Gate new blocking or timed code the same way, and run `cargo xtask check-web` (needs Chrome) after touching it.

7. The shader a kernel runs is its embedded WGSL artifact (`KernelDescriptor::artifacts`), checked by `gust::artifact::verify_artifact` against the descriptor (D17) before a pipeline exists; only a kernel without one, in a build with the `slang-runtime` feature (`dev`), is compiled by Slang at run time, and a strict build without the artifact is `Error::NoArtifact`. wgpu and the driver still compile the WGSL. A missing Vulkan adapter is `Error::NoAdapter`; report any other initialisation failure as what it is (the precompiled consumer prints `GPU initialization failed:` for those), so a test or CI step that expects "no adapter" cannot be satisfied by another error.

Read [headless execution](references/headless-execution.md) for buffer lifecycle and test requirements. `cargo xtask test-exact -p <package> --test <target> <name>` runs one existing standard Rust integration test by exact name with `--include-ignored` and rejects zero, ignored or repeated tests. It certifies test execution, not the test's implementation; inspect the test for real GPU assertions.

The SPIR-V route (m9.rt2, D172, D174; `crates/gust-wgpu/src/passthrough.rs`, `tests/spirv_route.rs`): with the feature `spirv-route`, `compile_kernel` builds a compute or pixel pipeline from slangc's SPIR-V (Vulkan only; another backend falls back with "backend is not Vulkan") through `create_shader_module_passthrough`, after `check_bindings`, and `densify_bindings` rewrites sparse `Binding` decorations to their rank in the layout (wgpu-hal renumbers densely; without it a write is lost on the RTX 5090 and the Radeon 890M crashes). Passthrough has no naga guards, so the macro emits index clamps, div/rem helpers and workgroup zeroing in the Slang. Every fallback to WGSL is recorded in `route_events()` with its reason; a test that claims the route must assert `Route::Spirv` there, because a silent fallback passes every value test. Run the Gpu suite with the feature on and off, and on both adapters.

Workgroup memory (M7, m7.g1): `Workgroup` arrays and the derived `LocalId`/`GroupId` are not resources, so a descriptor, a bind group and a `dispatch_buffers` slice list never mention them. A buffer that holds one value per workgroup (a block reduce's partials) has a length other than the element count, so bind it with `BufferBinding::read_write(..).independent_length()`; the dispatch otherwise refuses it as `BufferLength`.

Extents, resident vectors and the default device (M7, m7.d and m7.a0; D84, D102): `gust::Extent { x, y, z }` is what `call_extent`, `submit_extent` and `dispatch_extent` take (`call`, `submit` and `dispatch` mean `Extent::linear`). An axis of 0 runs nothing and is `Ok`; each axis is rounded up to whole workgroups, and the rounded product may be at most `Extent::MAX_INVOCATIONS` (2^32), else `Error::DeviceLimit` before any pipeline, uniform or upload exists. A `Shared` binding holds exactly `checked_total()` elements. `GpuVec<T>` stays on a device (`from_slice`, `zeroed`, `to_vec`; the `_on` forms take a `DeviceHandle`); its storage comes from the device's `BufferPool`, so the raw buffer behind it is the whole size class and a hand-written binding must be sized to `len()` bytes (`as_entire_binding()` shows the previous owner's tail; the generated host code still does this, see NEXT_TASKS). Zeroed hand-outs are cleared in a submission of their own. `default_device()` opens `DeviceOptions::default()` (high performance adapter; on native `LimitsPolicy::Adapter`, so the adapter's own buffer and binding limits, and on `wasm32` `LimitsPolicy::Default`; `features` is `FeaturesPolicy::Adapter` on native, which asks for `float32-filterable` when the adapter has it, and `FeaturesPolicy::Default` on `wasm32` and in `HeadlessDevice::new`, slice mx.t2), which `set_default_options` can change only before the first open (`Error::DefaultDeviceOpened`); `HeadlessDevice::new()` keeps wgpu's portable defaults, so a kernel that fits one can exceed the other's limits. Both request the capabilities of the build (`gust::capability::enabled()`, since M8), and `DeviceOptions::with_capabilities` replaces the set.

Textures and samplers (MX, mx.t2, D64, D90, D120; `crates/gust-wgpu/src/texture.rs`, `tests/textures.rs`): `GpuTexture2d<F>` comes from `create_texture_2d::<F>(width, height, TextureUse)`, texels go in with `write_texture` (tight row-major) and out with `read_texture` (native) or `read_texture_async` (the only one on `wasm32`; the 256-byte row padding is stripped), and `GpuSampler` comes from `create_sampler(SamplerOptions)`. The use is a promise that submit checks: a `Texture2D` parameter needs `SAMPLED` and a `StorageTexture2D` or `WriteTexture2D` one needs `STORAGE` (`Error::TextureUse`), the bound texture's format must be the parameter's (`TextureFormat`), and at creation a side over `max_texture_dimension_2d` is `DeviceLimit` named for that limit, while a zero side or a host slice of the wrong length is `TextureSize`. `wgpu_format` is the one `match` from `gust::texture::Format` to `wgpu::TextureFormat`, and wgpu's own `block_copy_size` and `sample_type` are reused, so add no second table. The bind-group layout is built per device in two variants. A linear sampler on an `f32` texture needs `float32-filterable` (`HeadlessDevice::float32_filterable()`), so it is `Error::TextureFilter` on a device that did not enable the feature (`HeadlessDevice::new()` and the browser do not; `DeviceOptions::default()` does when the adapter offers it), while a nearest sampler binds either way. A test that samples linearly must say which variant it ran in and must not skip silently. A write-only storage texture is bound `WriteOnly` in any of the nine formats, and `ReadWrite` exists only for the three `r32` formats (wgpu refuses it for wider ones). One texture bound to two parameters is `Error::AliasedBinding`, and the staged graph refuses a texture or sampler kernel (`Error::UnsupportedParameter`). Compare `load` and `store` bit for bit. Do not assert that a nearest sample next to a texel edge picks the twin's texel (in a probe the RTX 5090 picked the neighbour only at 2^-20 texel from an edge, and the tests use a 1/128 band), and bound a linear sample by `|gpu - twin| <= 2^-8 * (max - min) + 2 ulp` (SEMANTICS, D92).

The `pixel` call (MX, mx.p1b, D61, D120, D127; `crates/gust-wgpu/src/render.rs`, `tests/pixel.rs`, `tests/shape_refusal.rs`): a `pixel` kernel is a render pipeline held in the same cache and under the same key as a compute one (the key has the shape), with `FRAGMENT` visibility on its bind group. The typed `call`, `submit` and `dispatch` are those of `grid` minus the `_extent` forms. One call is one render pass of its own, in batch order: an `r8unorm` attachment 8192 wide and `ceil(n / 8192)` rows, `Load` and `Discard`, an empty write mask, and at most two scissored draws of `shapes/fullscreen.wgsl` (the full rows, then the tail row). The fragments write the kernel's storage buffers at `y * 8192 + x`, so nothing is read back from the attachment. Each of these is refused before any pipeline is built: a y or z other than 1 (also in a graph node), an indirect launch, the one-shot `dispatch_f32` and `dispatch_u32`, the generated host snippet, and an adapter without `DownlevelFlags::FRAGMENT_WRITABLE_STORAGE` are `Error::ShapeUnsupported { kernel, shape, reason }`; a read-write output bound `Independent` is `ShapeIndependentOutput`; `n` over `gust::PIXEL_MAX_ELEMENTS` (2^26) is `DeviceLimit` named `pixel_max_elements`, and an attachment wider than `max_texture_dimension_2d` is `DeviceLimit` named for that limit. `n = 0` is `Ok` and does no work. On `wasm32` wgpu reports every downlevel capability, so the capability refusal cannot fire in a browser and an adapter without it would give a wrong result instead: `examples/web-vector-add` (`check-web`) prints `GUST_OK` only when the pixel output equals the host reference and the `grid` output bit for bit, and `GUST_FAIL` when no fragment wrote. Test what a pixel call did, not only what came back. On these adapters robustBufferAccess2 drops an out-of-bounds store, so a stray fragment cannot show up as a wrong word, and `render.rs` counts the launched fragments with an atomic in a hand-written module instead (the count equals `n` at 1, 2, 8191 to 8194, `8192k + 1` and `8192k + 2` for k = 1, 2, 7 and 1000, and 2^26; `counted_sizes` in `render.rs`). Prefill every pixel output with a value the kernel cannot produce, compare `pixel`, `grid` and an independent host replay word for word (`differing_words` in `tests/pixel.rs`), and label the adapter. A word-for-word match between the shapes is the contract only for integer and `bool` outputs; for `f32` a bit difference between `pixel` and `grid` is an observation, judged within section 4's bounds (the difftest's interval) and not a kernel failure (D128, SEMANTICS section 1). The `f32`, `Vec2` and `Vec4` identity tests of `tests/pixel.rs` and `check-web` are stricter and compare bits, because their bodies are moves and one correctly rounded `f32` addition, with no multiply to fuse and no division, so the driver has no freedom to differ; a new `f32` body with a division or a multiply-add must not be added to a bit-for-bit gate. The identity tests are Gpu evidence on a hardware adapter (STATUS records the RTX 5090); on a software (`Cpu`-type) adapter they skip the sizes above `CPU_ADAPTER_MAX_ELEMENTS` with a printed `BRANCH` line, and that run is Gpu (software), never hardware. The identity test fails unless every size up to `CPU_ADAPTER_MAX_ELEMENTS` (1 000 003; 18 sizes) ran, so a software adapter cannot skip its way to green.

A debug-build Gpu test that dies with `0xc0000005` (`STATUS_ACCESS_VIOLATION`) when several GPU test binaries or threads run at once is the known crash in the Vulkan validation layer (`VkLayer_khronos_validation.dll`, its bundled mimalloc; STATUS m7.av3 and m7.av4). It has hit the `textures` and gust-algo binaries. Rerun the test alone and record that it crashed and passed on rerun; do not count the crash as a kernel failure or the rerun as a hidden retry. Do not disable validation in the gates. `VK_LOADER_LAYERS_DISABLE=VK_LAYER_KHRONOS_validation` is a diagnosis aid only.

Subgroup kernels (M8, m8.s, D140; `crates/gust-wgpu/tests/subgroup.rs`): a body that calls subgroup operations runs only on a device opened with `Capability::Subgroups` (`HeadlessDevice::new()` requests the capabilities of the build, `gust::capability::enabled()`), and `Error::SubgroupSize` refuses a workgroup that is not whole subgroups. The subgroup size is a property of the pipeline (32 on the RTX 5090, 64 on the Radeon 890M, 8 on lavapipe, 4 on WARP), so a test must never hard-code it: write `subgroup_size()` and `subgroup_lane()` beside the results and rebuild the subgroups of the host model from them, checking `lane == index % size` first. The same test file runs under `dev` (the portable bodies are selected) and `dev+subgroups`: `cargo xtask test --suite Gpu --profile dev+subgroups --test subgroup`, whose test count is `GPU_TARGET_PINS` in `xtask/src/verify.rs`. Use powers of two for `f32` inputs so that any combination order is exact, and a sentinel in the output to show a word no body wrote.

Capabilities, targets and the open-time refusal (M8, D142, D137, D145): a device is opened with a capability set (`DeviceOptions::capabilities`; `HeadlessDevice::capabilities()` and `subgroup_sizes()` report what it has), and a request the adapter cannot meet is `Error::MissingCapability { kernel: None, .. }` at open, so no device exists. On `wasm32` every non-empty request is refused whatever the adapter offers, because wgpu 30 cannot request subgroups in a browser; the browser page of `check-web` shows that this refusal runs there and proves nothing about the adapter, and the native unit tests over fake feature sets (`crates/gust-wgpu/src/device.rs`) pin both rules without a GPU that has subgroups. At launch a kernel whose `requires` the device lacks is `MissingCapability { kernel: Some(..), .. }`, a workgroup of partial subgroups is `SubgroupSize`, and a kernel passed by descriptor with `Target::Cpu` is `KernelTarget`; nothing is submitted in any of these. The typed entry points (and a staged graph's `run` and `run_indirect`) are bounded on the hidden `GpuKernel` marker, so a kernel routed to the CPU is a compile error (E0277) on a GPU device; a hand-written `Kernel` adds `impl gust::target::GpuKernel for X {}`. A test that needs subgroups runs under `dev+subgroups` and names the adapter and its subgroup size range.
