# Validation strategy

Validation is layered. Choose the cheapest command that can falsify the current claim, then widen only when the touched boundary requires it.

## Command tiers

| Situation | First check | Wider check | Release check |
| --- | --- | --- | --- |
| Validator/lowering/golden change | `cargo xtask check-feature macro` | `cargo xtask check-workspace` | `cargo xtask check-full` |
| Reflection/layout change | `cargo xtask check-feature reflection` | `cargo xtask check-feature gpu-runtime` | `cargo xtask check-full` |
| Semantics contract change (SEMANTICS.md, a ledger row, twin behaviour, `gust::cpu`) | `cargo xtask check-cpu` and `cargo test --locked -p gust-compute --lib cpu` | `cargo xtask check-feature gpu-semantics` (it runs the ledger test `mismatch`) and `cargo xtask check-dual --check-only` | `cargo xtask check-full` (adds the release ledger run and `check-dual` in full mode) |
| Loop dialect change | `cargo xtask check-feature loops` | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Result lowering/match | `cargo xtask check-feature result` | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Vector/matrix change (the `gust::math` types, swizzles, products, negation, the `vectors` and `products` goldens, StorageV2 buffers) | `cargo xtask check-feature vectors` (needs slangc, `spirv-val`, the reflection helper and an adapter) | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Uniform change (`Uniform<T>`, `ConstantBuffer<T>`, Std140, `write_uniform`, the `uniforms` golden) | `cargo xtask check-feature uniforms` (as for vectors) | `cargo xtask check-feature gpu-runtime` | `cargo xtask check-full` |
| Map/device options/buffer pool change (`gust::map`, `GpuVec`, adapter choice, limits, the parallel CPU map `gust::cpu::parallel`) | `cargo xtask check-feature map` | `cargo xtask check-feature gpu-runtime`, and `cargo xtask check-cpu-target` for the CPU map | `cargo xtask check-full` |
| Workgroup memory/barrier change (`Workgroup<[T; N]>`, `workgroup_barrier()`, `LocalId`, `GroupId`, the E0414 to E0416, E0717 and E0718 rules) | `cargo xtask check-feature workgroup` (needs slangc, `spirv-val`, `spirv-dis`, the reflection helper and an adapter) | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Capability, variant, subgroup or portable-floor change (`#[variant]`, `requires(..)`, `GUST_PROFILE=<target>+<capability>`, `gust::capability`, `gust::limits`, the subgroup functions, E0740 to E0747, E0750, E0751) | `cargo xtask check-feature macro` and `cargo xtask check-ui` | `cargo xtask test --suite Gpu --profile dev+subgroups` (slangc and an adapter), `cargo xtask check-difftest` (runs the `dev` and the `dev+subgroups` batch) and `cargo xtask check-examples` (builds `subgroup-reduce` under `native` and `native+subgroups`) | `cargo xtask check-full` |
| Routing change (`#[gpu(route = ..)]`, `[package.metadata.gust.routes]`, `gust.toml`, `cargo gust build\|check\|run\|test`, the `GpuKernel` marker) | `cargo xtask check-routing --check-only` (cargo only; the CI step) | `cargo xtask check-routing` (adds the GPU step), `cargo xtask check-dual` and `cargo xtask check-cpu-target` | `cargo xtask check-full` (does not run `check-routing`: run it beside) |
| `gust-algo` change (reduce, scan, compact, `variant::shipped`, `bound`) | `cargo xtask check-feature algo` (the adapter cases need slangc, the reflection helper and an adapter) | `cargo xtask test --suite Gpu` (it also pins the adapter cases by name, below) | `cargo xtask check-full` |
| `par_for!`, multi-dimensional dispatch (`Extent`) or readback change | `cargo xtask check-feature dispatch` | `cargo xtask check-feature map`, and `cargo xtask check-cpu-target` for the CPU `par_for!` case | `cargo xtask check-full` |
| Diagnostic sidecar maps | `cargo xtask check-feature core` | `cargo xtask check-workspace` | `cargo xtask check-full` |
| wgpu runtime/cache/buffer change | `cargo xtask check-feature gpu-smoke` or `gpu-runtime` | `cargo xtask check-feature wgpu` | `cargo xtask check-full` |
| GPU semantic feature | focused macro/golden test + one GPU feature test | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Example-only change | `cargo test -p <example> -- --include-ignored` | `cargo xtask check-examples` | `cargo xtask check-full` |
| Artifact/export change | relevant example binary | `cargo xtask check-artifacts` | `cargo xtask check-full` |
| Unknown dirty tree | `cargo xtask check-changed` | command it selects | `cargo xtask check-full` if release evidence is needed |

## Evidence tiers

Every status line, task report, and decision that cites evidence names the highest
tier it reached. A tier is claimed only with a run record (command, result, and for
Gpu the device).

| Tier | Claim | Typical command |
| --- | --- | --- |
| Unit | Macro validation, translation, and xtask logic pass without external tools; the declared minimum Rust version compiles every workspace target | `cargo test -p gust-compute-macros`, `cargo test -p xtask`, `cargo xtask lint` (CI), `cargo xtask check-ui`, `cargo xtask check-cpu`, `cargo test --locked -p gust-compute --lib cpu::tests::`, `cargo test --locked -p gust-compute --lib artifact::tests::`, `cargo test --locked -p gust-compute --test artifact`, `cargo xtask check-dual --check-only` (a separate step of the CI `unit` job, not of the Unit suite), `cargo xtask check-difftest --cpu-only --seeds 1-4` (a step of the Unit suite), CI job `msrv` |
| Cpu | The production CPU target (`GUST_PROFILE=cpu`) executes a kernel (scalar kernels and, since m6.x, a `Vec4` kernel), the calls of a generated map (m7.a1: `map`, `map_on`; since m7.c on a long input in parallel chunks, with the lowest-index panic) and `par_for!` loops (m7.p: one and two dimensions, sequential) and its output equals an independent host reference; it needs no external tool and no adapter, and the binary holds no Slang bridge, helper or GPU runtime. The thread count of the map is `GUST_CPU_THREADS` or the machine's parallelism; the check does not set the variable, so its parallel case (4 x 2^18 + 7 elements) runs on the caller's value or the machine's parallelism (up to four threads; one on a one-core machine) | `cargo xtask check-cpu-target` (the Cpu suite is this command; CI runs it as the job `cpu-target`, not in the Unit suite) |
| Slangc | The generated Slang compiles to the target | WGSL compile smoke tests, `cargo xtask check-fast` |
| Spirv | Exported SPIR-V passes `spirv-val --target-env vulkan1.2` | `cargo xtask check-artifacts` (the examples' files and the compiled goldens; below), `cargo xtask spirv-val <file.spv> --target-env vulkan1.2`, and `cargo xtask check-feature vectors` / `uniforms` for the golden area of those two (the other golden sets of `GOLDEN_SPIRV_SETS`, 11 of its 13, are made and validated by `check-artifacts`, the Spirv suite and `check-full`) |
| Reflect | The D17 layout gate matches the descriptor | `cargo xtask check-feature reflection` |
| Gpu | Readback on a device equals an independent host reference | GPU tests, `cargo xtask check-difftest` (generated kernels on the interpreter, the twin and the GPU), `cargo xtask check-full` |

Each tier is one command: `cargo xtask test --suite <Tier>`. Unit (which does not run `gust-algo`: the `unit` CI job stays free of wgpu) runs `cargo test --locked -p gust-compute-macros`, `cargo test --locked -p xtask`, lint, docs-check, check-arch, check-ui, check-cpu, `cargo test --locked -p gust-compute --lib cpu::tests::` (the `gust::cpu` unit tests; no slangc, no GPU), `cargo test --locked -p gust-compute --lib artifact::tests::` and `cargo test --locked -p gust-compute --test artifact` (`verify_artifact` on the committed precompiled fixture; no slangc, no GPU), the test binaries of `gust-compute` that need neither Slang nor the helper nor an adapter and were in no suite before m8.x1 (`--test pixel_twin`, `--test textures_twin`, `--test parallel`, `--test toolchain` and `--doc`, each counted so that a filter or a deleted file that leaves nothing to run fails), every test of `cargo-gust` that needs neither Slang nor the helper (`cargo test --locked -p cargo-gust -- --skip export::uniform_tests::the_helper_builds_the_stored_artifacts --skip testdata::variant::the_helper_builds_the_stored_artifacts --exact`, counted; `--exact` so that a test that only contains that text in its name is not dropped), `cargo clippy --locked -p gust-compute -p gust-compute-wgpu --no-default-features --lib -- -D warnings` and `cargo check --locked -p gust-compute -p gust-compute-wgpu --no-default-features --lib` (the `slang-runtime` off state; cargo only), then the format check, clippy and tests of the harness crate `tests/difftest` (a workspace of its own; m5.c2) and, last, `cargo xtask check-difftest --cpu-only --seeds 1-4` (the differential batch of 64 generated kernels, interpreter against CPU twin; cargo only, below). Slangc is Unit plus `cargo test --locked -p gust-compute --lib` and `cargo test --locked -p gust-compute --test diagnostics` (the Rust-line annotation of real Slang failures), the naga layout gate, and, since m8.x1, two named steps (each test required `ok` by its libtest name, so a renamed, moved, ignored or deleted test fails the step): the three helper-backed tests of `cargo-gust` (the real compile of the stored records of the export and of the variant fixture, and the schema 3 output of the built helper against the committed expectations; `--include-ignored` runs the two that are `#[ignore]`d) and `testdata::variant::` of `cargo-gust` under `GUST_PROFILE=dev+subgroups` (the stored variant records and manifest against what the macro makes, and the helper's output; the log line `checked under capabilities [Subgroups]: ` shows that the profile reached the test). Cpu is `check-cpu-target` alone (below); Unit does not contain it. Spirv is `check-artifacts`, Reflect is `check-feature reflection`, Gpu first names the adapter its tests will open (since m8.x1, so a log says which device it ran on) and then is `cargo test --locked -p gust-compute-wgpu` (since m5.f1, its `test result:` lines are checked against `GPU_SUITE_PIN`, as `verify --mode gpu` does), then `cargo test --locked -p gust-algo` (m7.r1: the reduce schedule, bound and golden tests, the CPU twins against independent references, and the `gpu::` tests on the adapter, each of which is required `ok` by name through `ALGO_GPU_TESTS`, as `verify --mode gpu` does after the wgpu call), followed by `cargo xtask check-difftest` (all 8 seeds and the `short_circuit` GPU test; a missing adapter fails), and Full is `check-full`, which also runs `cargo test --locked --release -p gust-compute --lib -- slang cpu::tests::invocations_are_capped_at_the_id_range_in_release` so that the release-only (`cfg(not(debug_assertions))`) tests run (the source-map fallback and the `gust::cpu` id-range cap, each required `ok` by name), and `cargo test --locked --release -p gust-compute-wgpu --test mismatch -- --nocapture` so that the known-mismatch ledger (`docs/SEMANTICS.md`) also runs with `overflow-checks` off (the Gpu suite runs it with checks on). That call is guarded like the release Slang tests (m5.f1): at least one test ran, `0 failed; 0 ignored`, and each of the six ledger tests (`RELEASE_LEDGER_TESTS` in `xtask/src/verify.rs`) reported `ok` by name, so an `#[ignore]`d, renamed or deleted ledger test fails the gate; `cargo xtask check-ledger` runs exactly that call with that guard. The call has `--nocapture`: the guard reads standard output only, and the release evidence (the adapter, the detected `overflow-checks` mode and the `S2 |` rows, which the tests print on standard error) is in the step's log and in the ledger files. Full also runs, last, the whole `check-precompiled` (not `--check-only`), the whole `check-web` (m4.i) and `check-difftest` (m5.c2: all 8 seeds on the adapter and the `short_circuit` GPU test). Nothing is skipped silently: a missing Chrome, `wasm-bindgen-cli`, wasm32 target or WebGPU adapter fails the run with the check's own message, and only `cargo xtask check-full --skip-web` goes without the browser run, which it prints and records (`skipped_checks`, below). The export and `spirv-val` steps of `check-artifacts` are part of the Full mode itself. Since m8.z Full also runs, after the workspace tests (the plain `dev` run) and the strict `subgroup-reduce` example, one more recorded step, `test --suite Gpu --profile dev+subgroups`: the pinned gust-wgpu targets (`capabilities`, `subgroup`) and then every test of `gust-algo`, each with the capabilities line of its own build required, so that the subgroup body of `gust-algo` and the subgroup cells run in the release gate (they did not before: the plain run selects the portable bodies). It needs an adapter with subgroup operations and fails, never skips, without one. A suite prints what it does not cover, and a pass of one tier says nothing about the tiers above it.

The run-time Slang bridge is the `slang-runtime` feature of `gust-compute` and `gust-compute-wgpu`, off by default (D44). The examples enable it in their manifests, and `gust-compute` and `gust-compute-wgpu` enable it for their own tests through a dev-dependency on themselves, so no test command here needs `--features`. The workspace build therefore unifies the feature on, and the off state is observed by the last two steps of the Unit suite, `cargo clippy --locked -p gust-compute -p gust-compute-wgpu --no-default-features --lib -- -D warnings` and `cargo check --locked -p gust-compute -p gust-compute-wgpu --no-default-features --lib` (cargo only: no slangc, no GPU); they are the only steps that build `gust-compute-wgpu` that way. `cargo xtask check-ui` and the `tests/dual` steps of `cargo xtask check-dual` also build `gust` without the feature, as a side effect. A unit test of xtask pins that the manifests set no default feature and no `features` on the `gust` entries of the workspace root and of `gust-wgpu`. Every cargo child that `cargo xtask` starts for the workspace runs under `GUST_PROFILE=dev`, whatever the parent has; a preset other value is logged and overridden. The profile itself is decided in `crates/gust/build.rs` (unit-tested from `cargo test -p gust-compute --lib profile::`): `GUST_PROFILE` is `dev`, `native`, `web` or `cpu`, any other value (an empty one included) fails the build, and a release build with the variable unset is `native` (`web` on `wasm32`) with a warning, so `cargo test --release` outside `cargo xtask` needs `GUST_PROFILE=dev`. A strict profile refuses the `slang-runtime` feature in that script and makes a kernel without an artifact a compile error at the kernel (`gust::profile::require_artifact`). `cpu` (D21, D51) refuses the feature in the same script, and `gust-wgpu` fails to compile under it (`gust::profile::require_gpu_target`); `cargo xtask check-cpu-target` proves both. `cargo xtask check-ui` proves four of the strict-profile cases with the fixtures `profile-native-no-artifact` (E0080 at the kernel line under `native`), `profile-dev-no-artifact` (the same file compiles under `dev`), `profile-unknown` and `profile-empty` (the build script refuses the value) and `profile-native-bridge` (`native` with the feature on is refused); a fixture gets its own variables from an `env.txt`, set after the workspace `dev`, and a `build-error:` line in its `expected.txt` names text of the build script's refusal in cargo's stderr. Switching between plain `cargo` (no `GUST_PROFILE`) and `cargo xtask` (`dev`) rebuilds `gust` and its dependents, because the build script reruns when the variable changes.

Label format: `done (Gpu: NVIDIA GeForce RTX 5090, Vulkan, slangc 2026.21, <commit>)`. The `Cpu` tier is labelled
`done (Cpu: <commit>)`. It is distinct from Unit, whose twin runs under `cfg(test)` (shadow-semantics evidence), and it
is never GPU evidence (D42): a CPU result proves nothing about an adapter.

**Labels of MX (execution shapes and textures; D61, D62, D95, D128).** The tiers do not change, and `pixel` gets no tier
of its own: for integer outputs it is inside D22's exact contract, for `f32` outputs it is under section 4 (D128), and
`sample` is a documented SEMANTICS limitation under the Gpu tier, not a tier. A Gpu line for shape work names the shapes
it executed, so a `grid` run cannot be read as a `pixel` one:

- `done (Gpu: NVIDIA GeForce RTX 5090, Vulkan, slangc 2026.21, <commit>; shapes grid, pixel)`;
- the browser: `Gpu (WebGPU, Chrome <version>, <vendor> <architecture>; shapes grid, pixel)`;
- software: `Gpu (software: lavapipe <name as wgpu prints it>, Mesa <version>, Vulkan, slangc <version>, <commit>;
  shapes grid, pixel)`.

The `; shapes ..` part is written by the person who writes the status line. No command prints it yet: `check-web` prints
`Gpu (WebGPU, Chrome <version>, <vendor> <architecture>)` and the record of `verify` has no field for the shapes (the
difftest report does: its `shapes` section). Which shapes a command ran is in its own documentation: `check-web` runs
both forms of `web-vector-add`, `check-difftest` runs `grid` unless it is given `--shapes grid,pixel`, and `cargo test
-p gust-compute-wgpu` runs `grid` and `pixel` (`tests/pixel.rs`). Every MX Gpu record is WGSL evidence: `gust-wgpu` executes the
WGSL that slangc emits (D82), and the SPIR-V of the textures and `pixel` goldens is Spirv tier (`spirv-val`) only;
executing SPIR-V is a 0.1.x slice after 0.1.0 (D95 placed it in MR, the MR plan's Q5 deferred it, D132; NEXT_TASKS,
slice mr.v). Hardware means the RTX 5090; the Radeon 890M took part in the spikes behind D120
and D127 and runs no gate; the software adapter is `Gpu (software)` and never stands in for hardware. Nothing in the
repository claims anything about a phone or a tile-based GPU: that hypothesis is untested (NEXT_TASKS).

*The reserved `Body` tier (D62, D95).* A shape with a per-function contract (Breeze's `vertex` and `raster_fragment`)
would be exact only on the inputs the body receives, with rasterization, interpolation, derivatives and fixed-function
stages outside the contract (D39). Its label, reserved here and used by no line, command or record of MX, is `done
(Body: <adapter>, <backend>, slangc <version>, <commit>)`, and its first use is with Breeze. No xtask code knows the
name; a line may not claim it until a decision row gives the tier its command.

**Vectors, uniforms and SPIR-V (slices m6.x, m6.x fix round 1).** The examples export SPIR-V, and no example uses a
vector, a matrix or a uniform, so `check-artifacts`, the Spirv suite and `check-full` (the Artifacts and Full modes of
`verify`) also compile the goldens in `tests/fixtures` (`vectors` and `products`; `uniforms`) to SPIR-V into
`<target>/golden-spirv/<area>/` with the pinned `slangc`, `-matrix-layout-column-major` and
`-fvk-use-entrypoint-name`, require exactly the file names pinned in `xtask/src/checks.rs` (`products__run.spv`,
`vectors__run.spv`, `uniforms__run.spv`; a golden that gains a kernel changes the list in the same commit, and the
list is kept apart from `EXPECTED_SPIRV`, which names the examples' files) and run `spirv-val --target-env vulkan1.2` on
each, recorded in the run like the examples' files. That is Spirv-tier evidence for those modules.
`cargo xtask check-feature vectors` and `uniforms` make and validate the same files for one area, then run the GPU
tests of the feature, so its Gpu claim is the RTX 5090 (or whichever adapter) named in the run record.

**Golden sets of M7 (slice m7.x1).** The same step compiles seven more golden sets of `tests/fixtures`: `map`, `grid`,
`workgroup`, `par_for`, `reduce`, `scan` and `compact`, nine sets with the two above (`GOLDEN_SPIRV_SETS` in
`xtask/src/checks.rs`). No example exports the SPIR-V of these kernels, so nothing else covers it. A golden of several
kernels is compiled one section at a time (`shader::golden_sections`). Each set pins its file names, sorted, and a
mismatch fails the run. An entry that does not carry the golden's name keeps its own
name (`map__add_one_map_kernel.spv`), and the names of the `par_for` set hold the hash of the lowered Slang of each
call, so a lowering change that re-hashes a body changes that list in the same commit; the unit tests of xtask
catch a stale list. This is Spirv-tier evidence (the files pass `spirv-val`), not Gpu evidence; the Gpu tests of each
area run through its `check-feature` command.

**Golden sets of MX (slices mx.t3 and mx.p1a).** `GOLDEN_SPIRV_SETS` has eleven areas, the nine above and two more:
`textures` (8 files, `textures__<kernel>.spv`, from `tests/fixtures/textures.slang`) and `pixel` (3 files:
`pixel__pack`, `pixel__row`, `pixel__shade`, fragment entries). A fragment is compiled with `-stage fragment`:
`shader::shader_entries` reads each entry's stage from its `[shader("..")]` line. The example `texture-threshold` adds
`threshold__mark.spv` to `EXPECTED_SPIRV`. As above, this is Spirv-tier evidence only, and the executed shader is the
WGSL.

`cargo xtask spirv-val`, `check-artifacts`, the Spirv suite, `check-full` and the `check-feature` areas that validate
SPIR-V print an informational `OpCopyLogical` count per module, read from `spirv-dis` (a missing `spirv-dis` is said in the line); it is never a failure. Slang emits that
instruction for copies between aggregates of different layouts, and naga's SPIR-V front end refuses it, which is the
whole reason the count exists: GUST's SPIR-V targets Vulkan drivers, and feeding it to naga is unsupported. The
executed route is WGSL. WGSL of the M6 constructs is judged by wgpu's own module creation in the GPU tests (wgpu's
default capabilities), not by a naga run with every capability enabled, which passed WGSL that wgpu refuses. Known
limit: a constant `Mat2` or `Mat3` handed to wgpu as SPIR-V crashes the runner (the faulting layer is not isolated;
SEMANTICS section 4). That is not a statement about the other cases: no M6 GPU case executes SPIR-V, because
`gust-wgpu` is fed WGSL, so every M6 Gpu result is WGSL evidence and the Spirv tier of M6 is `spirv-val` of the
exported modules. Matrix and uniform layout decorations in SPIR-V have never been executed. `cargo xtask slangc` compiles with the same matrix flag
as `gust`: a unit test reads the bodies of `gust`'s `slangc_command` and `slangc_reflection_command` and requires the
flag in each (the whole argument lists of those two are pinned by their own tests in `gust`).

**The naga layout gate (slice mx.n).** `crates/gust-wgpu/tests/naga_layout.rs` parses and validates WGSL with the naga
that wgpu runs (`wgpu::naga`, the lockfile's version; `Capabilities::empty()` for the front end and the validator and
`ValidationFlags::all()`, as `create_shader_module` does, never the all-capabilities default of
`naga::front::wgsl::Options`) and compares the `proc::Layouter` size, alignment and field offsets of every storage and
uniform binding's element type with the descriptor's layout. The WGSL is every compute and fragment entry of 19 of the
20 goldens of `tests/fixtures` (not `par_for`, whose kernels have no nameable descriptor), compiled by the `slangc`
command line with the stage of its shape (96 entries); every fixture kernel, compiled through the native reflection
helper, which is the route `HeadlessDevice` compiles through (106 kernels, 10 of them kernels that no golden holds; 202
modules in all, with the 96); and the committed precompiled WGSL. The test pins those counts, and the golden and fixture
`.rs` lists against the directory. It needs `slangc` on `PATH` and the helper (`GUST_SLANG_REFLECT`) but no adapter, and
it fails with a message naming the missing tool; it does not check a `slangc` version (the CI job `slang` installs the
pinned one). It runs in `cargo xtask check-feature reflection`, in the Slangc suite (the CI job `slang`) and in `cargo
test -p gust-compute-wgpu`, hence in `verify --mode gpu` (the CI job `gpu-software`), where its 9 tests and one result line are
counted in `GPU_SUITE_PIN`; the file takes about 15 s on the Windows development machine. It executes nothing, so it is
WGSL-validity and layout evidence, not Gpu evidence.

**The gust-algo Gpu suite step (slices m7.r1 to m7.r4, D121).** After the `gust-wgpu` call, `verify --mode gpu` and
the Gpu suite run `ALGO_GPU_CALL`, `cargo test --locked -p gust-algo` (`xtask/src/verify.rs`), so the `gpu-software`
job runs it on lavapipe too; the Unit suite does not, which keeps the `unit` job free of wgpu. The tests of the crate
are of two kinds. `twin::`, `schedule::`, `bound::`, `golden::`, `variant::` and `struct_gather::` need no adapter:
the schedule and bound arithmetic, the goldens of the reduce, scan and compact kernels, the v0 CPU twins (and the
twin of the worked struct gather) and the record of which variant ships
(`the_shipped_variants_are_the_measured_ones`). `gpu::` runs the same cases on the first Vulkan adapter, v0 and v1
both, and never skips: with no adapter it fails. Every case has an independent reference (a sequential `f64`
accumulation, an `i128` sum, `Iterator::min`), and the twin and the GPU are each compared with it, never with each
other. Integer sums, `min` and `max` are exact at the schedule boundaries, `sum_wrapping` is exact modulo 2^32, and a
float sum is within the per-level bound of the variant that ran (`gust_algo::bound`). `ALGO_GPU_TESTS` lists the
`tests::gpu::` tests by name and `check_algo_gpu_counts` judges the output of the call: tests ran, none ignored,
every listed test reported `ok`, and the number of `tests::gpu::` tests that passed equals the length of the list, so
a deleted, renamed, ignored or unlisted adapter test fails the step. Adding or removing one changes the list in the
same commit, as for `GPU_SUITE_PIN`. The deepest-schedule cases want a binding of 2^26 + 1 `u32` (256 MiB), which the
portable limits and lavapipe's 128 MiB do not allow: below that limit they say on standard error that the three-pass
reduction did not run, assert the `DeviceLimit` refusal, and run the deepest input that fits (the m7.r4 erratum in
STATUS). The v0 against v1 measurement behind `variant::shipped` (interleaved end-to-end runs on the RTX 5090 and the
Radeon 890M) is not part of the gate; its logs are in the work area and D121 records the outcome.

**The Slang pin (D46, slice m4.r; moved to 2026.21 by D150, slice m8.p).** `cargo gust` is pinned to the Slang 2026.21
release, and `VALIDATED_BUILDS` ships empty. 2026.21 was validated on Windows with the release archive itself (spike
SL21, then slice m8.p): every committed artifact set was re-blessed with that slangc and a helper built against it
(the WGSL is byte-identical, only the compiler tag and what follows from it changed), the Spirv, Reflect, Slangc and Gpu
suites ran on the RTX 5090, and D141's fix-up was re-checked on the new WGSL. Only the Windows archive of 2026.21 has
been executed: the Linux archive (`slang-2026.21-linux-x86_64.tar.gz`) is first run by CI's `slang` job, and the macOS
archive has no job and stays unexecuted; both are digest and size entries compared with GitHub's published values.
The history of the 2026.20 pin follows, as written for slice m4.r. It was validated on Windows with the release archive
itself: every committed artifact set was re-blessed with that slangc and a helper built against it, the Spirv, Reflect
and Gpu suites ran on the RTX 5090, and the three
particle-step SPIR-V modules that changed with the bump were executed on the adapter and read back equal to the
2026.13.1 ones. The Linux archive (`slang-2026.20-linux-x86_64.tar.gz`) and the macOS archive were never executed
before that slice: CI, whose `slang` job installs the pin with the manager, builds the helper with g++, runs the
Slangc tier and re-checks the committed `tests/precompiled` artifacts with `cargo gust check --recompile` (so a pin
bump without a re-bless fails there), and whose gpu-software job does the same on lavapipe, had run the 2026.20 Linux
archive: the `slang` job was green on `af0c2b6`, and its recompile step took 5 s. That run is the evidence for that platform,
and a red run there would have been a finding about the archive, not about the Windows evidence. The macOS archive has
no CI job and stays unexecuted.

**The reflection helper in `cargo xtask` (slice m4.r).** `verify` (the Spirv suite), `check-feature reflection` (the
Reflect suite) and `doctor` use the helper that `GUST_SLANG_REFLECT` names when it is set to a file other than this
checkout's own `target/slang-reflect` output, and build none of their own. Its `--version` Slang tag must equal the pin
in `SLANG_PIN` of `crates/gust/src/toolchain.rs` (and, for `verify`, the output of `slangc -version`); a helper of another build,
such as one built on 2026.13.1, is refused with a message that names both tags. When the variable is unset, the helper
is built from `SLANG_SDK` or `VULKAN_SDK` as before, and the result must carry the pin as well, so an SDK of another
version is refused instead of being used silently (a VulkanSDK that ships 2026.13.1 therefore needs `SLANG_SDK` to
name the managed 2026.21 install). `cargo gust slang build-helper` (which `cargo xtask build-slang-reflect` runs)
keeps a helper only when a build stamp beside it holds the SHA-256 of the packaged C++ source and the helper prints
the Slang tag of the SDK's own `slangc -version`; no file time plays a part (slice m4.z). Any other helper in the
output directory is rebuilt, and the build says why. A helper built before the stamp existed is rebuilt once.
`cargo gust doctor` warns when the first `slangc` on `PATH` is not the pin, naming both versions.
The pin is not enforced on every path. `cargo gust build` and `check --recompile` require the pinned `slangc` and a
helper of the same build; `cargo xtask` checks the helper's tag against the pin, and `verify` requires both
`slangc -version` and the helper's tag to equal the pin. A plain `cargo gust check` compares the helper's tag with the
manifest's and does not run `slangc -version`, so a matching older Slang passes it. `gust::slang`, the run-time bridge
of `dev` builds, checks no version at all (NEXT_TASKS, "M4 follow-ups").
A software Vulkan driver such as lavapipe counts as `Gpu (software)`, never as
hardware evidence. Expected values come from an independent host reference, never from
the shadow bodies (D04). A missing tool or adapter is a failure for its tier, not a skip.

**The additive rule for CPU twins (D26, M3).** A twin assertion adds to the host-reference and GPU assertions of a test
and never replaces either. The twin half needs no adapter, so where it runs alone (`check-cpu`, the `gust::cpu` unit
tests) it is Unit-tier evidence of the shadow semantics; it is never GPU evidence and never the expected value. A test that has a GPU half still compares the GPU readback with
the independent host reference, and the twin is compared with both. A known difference between the twin and the GPU is
a row of the known-mismatch ledger in [SEMANTICS](../SEMANTICS.md) with a measured GPU outcome, not a loosened
assertion, and a difference at an edge case is documented, never chased (D39).

## The Gpu (software) tier (D52)

The workflow `.github/workflows/gpu-software.yml` (job `gpu-software`, `ubuntu-24.04`) runs the Gpu suite on Mesa lavapipe, a software Vulkan implementation, as `cargo --locked xtask verify --mode gpu --record` (the same `cargo test --locked -p gust-compute-wgpu` as the Gpu suite, plus the adapter record). It runs on push to `main`, on pull requests, on `workflow_dispatch` and nightly (`schedule`, 03:00 UTC), and is never a required check: a red run is visible and blocks nothing. The jobs and their lists are in the paragraph that follows the one on what it does not prove. `VK_DRIVER_FILES` points at `lvp_icd.json`, so lavapipe is the only device even if a runner image exposes another driver. Label: `Gpu (software: lavapipe <name as wgpu prints it>, Mesa <version>, Vulkan, slangc <version>, <commit>)`. The workflow uploads `.ai/VALIDATION.json`, the log of the run and the apt and `vulkaninfo` identity as the artifact `gpu-software-<run id>`.

What a green run proves: the Gpu suite's readbacks equal their independent host references on a conforming software Vulkan implementation, with a reproducible driver. The workflow asserts on the record that the adapter is `"device_type": "Cpu"`, that its name contains `llvmpipe`, and that `driver_info` is exactly the pinned string (`MESA_DRIVER_INFO`, Mesa package version and LLVM version); `cargo xtask verify --mode gpu` itself checks the log (slice m5.a2): every `test result:` line must read `ok` with `0 failed; 0 ignored`, the `passed` counts must sum to the pinned number (`GPU_SUITE_PIN.passed` in `xtask/src/verify.rs`) and the number of result lines must equal `GPU_SUITE_PIN.result_lines`; a mismatch fails the mode, names both numbers and is written into the record. Both were measured by the run on the pull request (run 41311817894): 123 passed over 17 result lines (146 over 20 when m5.a2 moved them). Every slice that adds or removes a Gpu test or test file changes them in the same commit, and the doc comment of `GPU_SUITE_PIN` gives the command that recomputes both; drift fails the job by design. The check runs in the Gpu mode on every adapter, so a local `verify --mode gpu` on the RTX 5090 enforces the same numbers. Since m5.f1 `cargo xtask test --suite Gpu` checks the same pin (it makes the same call and prints the same line). The pin is not checked anywhere else: the Fast mode makes the same cargo call, and `check-full` does not make it at all, so a dropped Gpu test file is caught by `verify --mode gpu` or the Gpu suite, never by `check-full` alone (the gates of a slice run both). `cargo xtask status` prints `tier=Gpu (software)` after the usual fields when the record's `device_type` is `Cpu`, so a local record from lavapipe cannot read as hardware.

What it does not prove: anything about a hardware driver (subgroup behaviour, memory model, timing, performance, driver bugs of a vendor), so a `done (Gpu: ...)` label keeps naming a hardware adapter and a software run may be listed beside it, never instead of it. It does not run the Unit job's checks, `check-artifacts` or `check-dual`; `check-examples` and the release-profile ledger are in the nightly list below. A SEMANTICS line stays *measured*, not *proven*, with two adapters listed, and a difference between the two adapters inside the defined domain is a failure to investigate, never a second observation. Edge-case differences stay documented limitations (D39).

## The differential batch (slice m5.c2, plan M5 R1-13)

`cargo xtask check-difftest [--seeds <list|range|random:N>] [--cpu-only] [--shapes grid[,pixel]] [--report PATH]` runs the generator, the
interpreter, the CPU twin and (without `--cpu-only`) the GPU on generated scalar kernels, through `difftest-run` of
`tests/difftest` ([DIFFTEST](DIFFTEST.md)). It does not reimplement the harness: it runs it, reads the `report.json` by
fields and fails unless the report has the requested mode and seeds, `programs_executed` equal to 16 times the seeds
(so a run that silently executed fewer programs fails and the message names both numbers), no mismatch (each is named
with its seed, program and kind), and, without `--cpu-only`, an adapter. Without `--cpu-only` it also runs the harness
crate's `short_circuit` test with `--ignored`, which the plain `cargo test` of that crate leaves out: the GPU must not
evaluate a right operand of `&&`/`||` that the left operand makes unnecessary (the WGSL that Slang emits is read for
it). The default is the 8 seeds of `tests/difftest/seeds.txt` (128 programs). `random:N` draws N seeds from the clock,
prints them and runs them as a list, so a failure is reproduced by naming that list. `--shapes grid,pixel` (slice mx.p1c)
also runs every program as a `pixel` kernel and requires the pixel GPU bits to equal the grid GPU bits for integer and boolean outputs (an `f32` pixel output is judged against its interval like the grid one, and the bit difference between the shapes is only recorded: a device may fuse and round per stage, D128); a program whose
pixel pin the macro refuses stays `grid`-only and is counted with the macro's reason. Two callers ask for it: `check-full`, and one step of the `gpu-software` workflow
(seeds 1-2, lavapipe, on both of its lists; slice mx.z); the command line, the Gpu suite and ci.yml do not. Like
the rest of the batch it proves values only: a fragment outside the `n` elements is invisible under robust buffer access.

| --- | --- | --- | --- |
| Unit suite (and so the Slangc suite), CI job `difftest` (the `unit` and `slang` jobs pass `--skip-difftest`) | `cargo xtask check-difftest --cpu-only --seeds 1-4`, after the format check, clippy and tests of `tests/difftest` | Unit (interpreter against CPU twin; shadow-semantics evidence, never GPU evidence) | 64 |

What a pass proves: for the generated programs of those seeds, which are in-domain kernels over scalar `u32`, `i32`,
`bool` and `f32` buffers (with vector and matrix locals since DIFFTEST_FORMAT 6) of the operator set of DIFFTEST
(R1-4), the GPU output equals the interpreter's output (integers and booleans exactly, floats inside the interval
the interpreter derived), the CPU twin equals it bit for bit, and the harness executed every planned program. What
it does not prove: anything about programs outside the generator's space (no loops over runtime bounds, no atomics,
no structs, no vector or matrix buffers or results, and none of the vector and matrix forms DIFFTEST lists as
never written by the seeds run), anything about a seed that was not run, anything about
another driver than the one named in the report, or, for the `--cpu-only` run, anything about a GPU at all. The Unit
run cannot see a Slang or driver fault; a program the interpreter rejects is discarded and counted in the report, not
run. That includes the programs discarded as `static` (a constant the shader compilers may refuse at shader-creation
time): the corpus keeps none, so the batch says nothing about what the compilers do with them. Since DIFFTEST_FORMAT 5
a non-literal divisor goes through `__gust_div`/`__gust_rem`, which slangc does not fold (D77), so a zero divisor in a
dead branch no longer fails with E30002; a literal zero divisor is E0317, and the remaining limits are in
[DIAGNOSTICS](../DIAGNOSTICS.md). Since DIFFTEST_FORMAT 7 (m8.x1) each result file also carries the
capabilities its run crate was built for, and the reader refuses a result of another format (the program space is
format 6's; [DIFFTEST](DIFFTEST.md) has the flags). A harness failure (exit 2: a build error, a stale template
lockfile, a result file missing) fails the command as well and is never reported as a pass; a report left by an
earlier run cannot pass the next one (the file is removed first). Measured costs are in DIFFTEST, "Gates".

## Subgroup evidence (slice m8.e, M8; D140, D146, Opus 14)

The subgroup form of the reduction's per-block step was measured against the shipped v1 before it was allowed to become
a variant. The shipped step is `sum_u32_block` (`crates/gust-algo`, one workgroup of 256 lanes per 8192 elements, a
32-term lane chain, an eight-round shared-memory tree); its subgroup form (`gust_algo::evidence`) keeps the lane chain
and replaces the tree by one `subgroup_add`, one write of each subgroup's total to workgroup memory, one barrier and a
sum of the at most 32 totals. The program is `crates/gust-algo/examples/sg_ab.rs`, a release build under
`GUST_PROFILE=dev+subgroups`; it times one `u32` sum end to end (the batch, the fence wait and the read-back of the
result), as the m7.r4 `ab` example does, after five warm-up pairs, and checks both forms against the host sum on every
call. A *run* is the median of 200, 100 and 30 calls at 1e6, 1e7 and 1e8 elements. Three runs of each form were taken
interleaved (v1, subgroup, v1, subgroup, v1, subgroup). The rule was registered before the first run: the subgroup form
is faster at a size only when its **slowest** run is below v1's **fastest**, and it becomes the `requires(subgroups)`
variant of the shipped kernel only if it is faster at every size on both adapters; otherwise it stays a separate
evidence kernel and the shipped kernel is untouched. No size was run twice.

v1 ran first in every pair. Under a downward drift of the run times across the three runs (on the RTX 5090 at 1e7 both
forms drift down: v1 456.5 to 393.6 µs, subgroup 430.7 to 349.9) that order favours the form that runs second, but the
rule compares the subgroup form's slowest run, an early one under such a drift, with v1's fastest run, a late one. A
downward drift therefore makes "faster" harder to reach, not easier: the order cannot have produced a false "faster".
It could have hidden a small real gain, so the outcome below reads "no gain shown by this method", not "no gain". A
smoke run at 1e5 elements on the RTX 5090, taken before the series to check the harness and not a table size, gave a
v1 median of 397.2 and a subgroup median of 414.5 µs (not faster).

Measured 2026-11-08, a quiet window (the RTX 5090 held 2769 MiB of 32607 MiB at 0 % utilisation before every
size, read with `nvidia-smi`; nothing on the 890M was monitored beyond that), slangc 2026.21, Vulkan. Times are microseconds per sum; the three runs, then the median
of the three.

Outcome: the subgroup form is not faster in any of the six cells, and the medians are within 11 % of each other in
both directions (0.97 to 1.11 v1 over subgroup), so it is **a separate evidence kernel**: `variant::shipped`, the
public reductions, `tests/fixtures/reduce.rs` and the goldens are unchanged, and `Variant` has no third member. The
closeness has two different causes. At 1e6 and 1e7 on the RTX 5090 the medians are about equal (about 400 µs) and the
fastest single calls are 250 to 280 µs: the fixed cost of one end-to-end call (submit, fence wait, read-back)
dominates there, so the method cannot see the tree's barrier cost at those sizes, and the run medians vary by up to
about 25 % within one form (v1 at 1e7: 456.5 to 393.6 µs). At 1e8 on the RTX 5090 and on the Radeon rows the time
grows with the data, which fits a reduction bound by memory traffic (not measured separately).

## What each scan sees

`cargo xtask lint` reads **tracked files only** (`git ls-files`). `cargo xtask docs-check` and `cargo xtask check-arch` read tracked files **plus untracked files that are not ignored** (the files the next commit would contain). A new script, or a new file with a machine-specific path, is therefore not caught by `lint` until it is staged with `git add`, while a broken link or a stray `ir` module is caught before that. Ignored files (`target/`, `generated-wgpu/`, `.ai/VALIDATION.json`) are scanned by none of them.

## Minimum Rust version

The workspace declares `rust-version = "1.90"` (D30, which supersedes the 1.88 in D29: the locked `ordered-float 5.5.0`, pulled in by wgpu-hal, declares 1.90). The CI job `msrv` measures the claim: it installs exactly Rust 1.90.0 and runs `cargo check --workspace --all-targets --locked` (all targets, so test code is covered). It needs no slangc and no GPU and runs no tests, so it is Unit-tier evidence of compilation only. It is not a required check yet. A local run needs a 1.90 toolchain: `rustup toolchain install 1.90.0`, then `RUSTUP_TOOLCHAIN=1.90.0 cargo check --workspace --all-targets --locked`. `cargo xtask check-full` uses the stable toolchain and does not measure the minimum version; `.ai/VALIDATION.json` lists it under `untested`.

## Record policy

Routine checks do not rewrite `.ai/VALIDATION.json`. Use `cargo xtask verify --mode <mode> --record` only when a durable record for a non-full mode is useful. `cargo xtask check-full` records by default and is the release-evidence path. The record carries `git_commit` (the output of `git rev-parse HEAD`, taken before the checks start) and `git_dirty` (true when `git status --porcelain --untracked-files=all` listed anything: modified, staged, or untracked files that are not ignored, whatever `status.showUntrackedFiles` says). Both are `null` when git is unavailable or refuses the repository. A record with `git_dirty: true` is evidence about that working tree, not about the commit. `cargo xtask status` prints them as `commit=` and `dirty=`; a record written before the stamp existed prints `unknown`. The record also carries `adapter` (m4.h): the Vulkan adapter that `HeadlessDevice::new()` selects in the example process, which uses the same selection logic as the GPU steps (it is a separate process, so the record does not prove that every later step ran on that adapter if the machine changes in between). It is read from the one JSON line that `cargo run --locked --quiet -p gust-compute-wgpu --example adapter_info` prints (`HeadlessDevice::adapter_info()`: `name`, `vendor`, `device`, `device_type`, `backend`, `driver`, `driver_info`; no path, and the usual redaction applies). Any Vulkan adapter satisfies the GPU tiers, a software one (lavapipe) included, so `device_type` (`Cpu` for a software adapter) says which ran. Every verify mode runs this step before its first GPU step: a failed run, an empty output, a second line, or a blank name, device type or backend fails the mode and the record then says `"adapter": null`. A record written before m4.h has no `adapter` member. It also carries `skipped_checks` (m4.i): the checks that `check-full --skip-web` was asked to leave out (`["check-web"]`), an empty list for a run that skipped nothing; a record written before m4.i has no such member, and `untested` still lists `browser WebGPU` there.

## Required evidence by boundary

- Validator: accepted fixture or single-cause rejection test with a meaningful diagnostic.
- Lowering: reviewed Slang golden plus a source-structure assertion when useful.
- Shader target: WGSL compile smoke in routine tests; SPIR-V validation in artifact/full checks.
- Runtime: real GPU readback against an independent host reference, including partial and multiple workgroups.
- Engine proof: explicit contract first, exact transfer/residency/count assertions, no silent fallback.
- Capability (M8): a claim about a subgroup operation names the adapter, its subgroup size and the profile it ran under
  (`dev+subgroups` is the test profile, `native+subgroups` the strict one); a refusal path (`MissingCapability`) is
  proved by its unit test over fake feature sets and, in a browser, by the page of `check-web`, which is not evidence
  about what that adapter offers. A route (M8) is `Cpu` evidence until `check-routing`'s `gpu` case has run on an
  adapter.

## What not to do

- Do not run `cargo xtask check-full` as the first check for a local compiler edit.
- Do not auto-bless goldens without reviewing the semantic diff.
- Do not treat `spirv::validate_structure` as semantic SPIR-V validation; external `spirv-val` owns that layer.
- Do not introduce shared `HeadlessDevice` fixtures until `cargo xtask measure-tests` isolates adapter/device setup as the bottleneck.
- Do not commit regenerated `generated-wgpu/` outputs; full/artifact checks regenerate
	them locally and validate the SPIR-V files before leaving them ignored. The Artifacts and Full modes
	(`check-artifacts`, `check-full`, the Spirv suite) empty `generated-wgpu/` before the examples export
	into it (m4.h), so the file of a deleted or renamed kernel cannot satisfy the name check or pass
	`spirv-val`; the other modes leave the directory alone.
