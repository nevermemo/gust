# Validation strategy

Validation is layered. Choose the cheapest command that can falsify the current claim, then widen only when the touched boundary requires it.

## Command tiers

| Situation | First check | Wider check | Release check |
| --- | --- | --- | --- |
| Validator/lowering/golden change | `cargo xtask check-feature macro` | `cargo xtask check-workspace` | `cargo xtask check-full` |
| Reflection/layout change | `cargo xtask check-feature reflection` | `cargo xtask check-feature gpu-runtime` | `cargo xtask check-full` |
| Semantics contract change (SEMANTICS.md, a ledger row, twin behaviour, `gust::cpu`) | `cargo xtask check-cpu` and `cargo test --locked -p gust --lib cpu` | `cargo xtask check-feature gpu-semantics` (it runs the ledger test `mismatch`) and `cargo xtask check-dual --check-only` | `cargo xtask check-full` (adds the release ledger run and `check-dual` in full mode) |
| Loop dialect change | `cargo xtask check-feature loops` | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Result lowering/match | `cargo xtask check-feature result` | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Vector/matrix change (the `gust::math` types, swizzles, products, negation, the `vectors` and `products` goldens, StorageV2 buffers) | `cargo xtask check-feature vectors` (needs slangc, `spirv-val`, the reflection helper and an adapter) | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Uniform change (`Uniform<T>`, `ConstantBuffer<T>`, Std140, `write_uniform`, the `uniforms` golden) | `cargo xtask check-feature uniforms` (as for vectors) | `cargo xtask check-feature gpu-runtime` | `cargo xtask check-full` |
| Map/device options/buffer pool change (`gust::map`, `GpuVec`, adapter choice, limits, the parallel CPU map `gust::cpu::parallel`) | `cargo xtask check-feature map` | `cargo xtask check-feature gpu-runtime`, and `cargo xtask check-cpu-target` for the CPU map | `cargo xtask check-full` |
| Workgroup memory/barrier change (`Workgroup<[T; N]>`, `workgroup_barrier()`, `LocalId`, `GroupId`, the E0414 to E0416, E0717 and E0718 rules) | `cargo xtask check-feature workgroup` (needs slangc, `spirv-val`, `spirv-dis`, the reflection helper and an adapter) | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| `gust-algo` change (reduce, scan, compact, `variant::shipped`, `bound`) | `cargo xtask check-feature algo` (the adapter cases need slangc, the reflection helper and an adapter) | `cargo xtask test --suite Gpu` (it also pins the adapter cases by name, below) | `cargo xtask check-full` |
| `par_for!`, multi-dimensional dispatch (`Extent`) or readback change | `cargo xtask check-feature dispatch` | `cargo xtask check-feature map`, and `cargo xtask check-cpu-target` for the CPU `par_for!` case | `cargo xtask check-full` |
| Diagnostic sidecar maps | `cargo xtask check-feature core` | `cargo xtask check-workspace` | `cargo xtask check-full` |
| wgpu runtime/cache/buffer change | `cargo xtask check-feature gpu-smoke` or `gpu-runtime` | `cargo xtask check-feature wgpu` | `cargo xtask check-full` |
| GPU semantic feature | focused macro/golden test + one GPU feature test | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Example-only change | `cargo test -p <example> -- --include-ignored` | `cargo xtask check-examples` | `cargo xtask check-full` |
| Artifact/export change | relevant example binary | `cargo xtask check-artifacts` | `cargo xtask check-full` |
| Unknown dirty tree | `cargo xtask check-changed` | command it selects | `cargo xtask check-full` if release evidence is needed |

## Evidence tiers

Every status line, task report, and decision that cites evidence names the highest
tier it reached. A tier is claimed only with a run record (command, result, and for
Gpu the device).

| Tier | Claim | Typical command |
| --- | --- | --- |
| Unit | Macro validation, translation, and xtask logic pass without external tools; the declared minimum Rust version compiles every workspace target | `cargo test -p gust-macros`, `cargo test -p xtask`, `cargo xtask lint` (CI), `cargo xtask check-ui`, `cargo xtask check-cpu`, `cargo test --locked -p gust --lib cpu::tests::`, `cargo test --locked -p gust --lib artifact::tests::`, `cargo test --locked -p gust --test artifact`, `cargo xtask check-dual --check-only` (a separate step of the CI `unit` job, not of the Unit suite), `cargo xtask check-difftest --cpu-only --seeds 1-4` (a step of the Unit suite), CI job `msrv` |
| Cpu | The production CPU target (`GUST_PROFILE=cpu`) executes a kernel (scalar kernels and, since m6.x, a `Vec4` kernel), the calls of a generated map (m7.a1: `map`, `map_on`; since m7.c on a long input in parallel chunks, with the lowest-index panic) and `par_for!` loops (m7.p: one and two dimensions, sequential) and its output equals an independent host reference; it needs no external tool and no adapter, and the binary holds no Slang bridge, helper or GPU runtime. The thread count of the map is `GUST_CPU_THREADS` or the machine's parallelism; the check does not set the variable, so its parallel case (4 x 2^18 + 7 elements) runs on the caller's value or the machine's parallelism (up to four threads; one on a one-core machine) | `cargo xtask check-cpu-target` (the Cpu suite is this command; CI runs it as the job `cpu-target`, not in the Unit suite) |
| Slangc | The generated Slang compiles to the target | WGSL compile smoke tests, `cargo xtask check-fast` |
| Spirv | Exported SPIR-V passes `spirv-val --target-env vulkan1.2` | `cargo xtask check-artifacts` (the examples' files and the compiled goldens; below), `cargo xtask spirv-val <file.spv> --target-env vulkan1.2`, and `cargo xtask check-feature vectors` / `uniforms` for the golden area of those two (the other seven golden sets are made and validated by `check-artifacts`, the Spirv suite and `check-full`) |
| Reflect | The D17 layout gate matches the descriptor | `cargo xtask check-feature reflection` |
| Gpu | Readback on a device equals an independent host reference | GPU tests, `cargo xtask check-difftest` (generated kernels on the interpreter, the twin and the GPU), `cargo xtask check-full` |

Each tier is one command: `cargo xtask test --suite <Tier>`. Unit (which does not run `gust-algo`: the `unit` CI job stays free of wgpu) runs `cargo test --locked -p gust-macros`, `cargo test --locked -p xtask`, lint, docs-check, check-arch, check-ui, check-cpu, `cargo test --locked -p gust --lib cpu::tests::` (the `gust::cpu` unit tests; no slangc, no GPU), `cargo test --locked -p gust --lib artifact::tests::` and `cargo test --locked -p gust --test artifact` (`verify_artifact` on the committed precompiled fixture; no slangc, no GPU), `cargo clippy --locked -p gust -p gust-wgpu --no-default-features --lib -- -D warnings` and `cargo check --locked -p gust -p gust-wgpu --no-default-features --lib` (the `slang-runtime` off state; cargo only), then the format check, clippy and tests of the harness crate `tests/difftest` (a workspace of its own; m5.c2) and, last, `cargo xtask check-difftest --cpu-only --seeds 1-4` (the differential batch of 64 generated kernels, interpreter against CPU twin; cargo only, below). Slangc is Unit plus `cargo test --locked -p gust --lib` and `cargo test --locked -p gust --test diagnostics` (the Rust-line annotation of real Slang failures). Cpu is `check-cpu-target` alone (below); Unit does not contain it. Spirv is `check-artifacts`, Reflect is `check-feature reflection`, Gpu is `cargo test --locked -p gust-wgpu` (since m5.f1, its `test result:` lines are checked against `GPU_SUITE_PIN`, as `verify --mode gpu` does), then `cargo test --locked -p gust-algo` (m7.r1: the reduce schedule, bound and golden tests, the CPU twins against independent references, and the `gpu::` tests on the adapter, each of which is required `ok` by name through `ALGO_GPU_TESTS`, as `verify --mode gpu` does after the wgpu call), followed by `cargo xtask check-difftest` (all 8 seeds and the `short_circuit` GPU test; a missing adapter fails), and Full is `check-full`, which also runs `cargo test --locked --release -p gust --lib -- slang cpu::tests::invocations_are_capped_at_the_id_range_in_release` so that the release-only (`cfg(not(debug_assertions))`) tests run (the source-map fallback and the `gust::cpu` id-range cap, each required `ok` by name), and `cargo test --locked --release -p gust-wgpu --test mismatch -- --nocapture` so that the known-mismatch ledger (`docs/SEMANTICS.md`) also runs with `overflow-checks` off (the Gpu suite runs it with checks on). That call is guarded like the release Slang tests (m5.f1): at least one test ran, `0 failed; 0 ignored`, and each of the six ledger tests (`RELEASE_LEDGER_TESTS` in `xtask/src/verify.rs`) reported `ok` by name, so an `#[ignore]`d, renamed or deleted ledger test fails the gate; `cargo xtask check-ledger` runs exactly that call with that guard. The call has `--nocapture`: the guard reads standard output only, and the release evidence (the adapter, the detected `overflow-checks` mode and the `S2 |` rows, which the tests print on standard error) is in the step's log and in the ledger files. Full also runs, last, the whole `check-precompiled` (not `--check-only`), the whole `check-web` (m4.i) and `check-difftest` (m5.c2: all 8 seeds on the adapter and the `short_circuit` GPU test). Nothing is skipped silently: a missing Chrome, `wasm-bindgen-cli`, wasm32 target or WebGPU adapter fails the run with the check's own message, and only `cargo xtask check-full --skip-web` goes without the browser run, which it prints and records (`skipped_checks`, below). The export and `spirv-val` steps of `check-artifacts` are part of the Full mode itself. A suite prints what it does not cover, and a pass of one tier says nothing about the tiers above it.

The run-time Slang bridge is the `slang-runtime` feature of `gust` and `gust-wgpu`, off by default (D44). The examples enable it in their manifests, and `gust` and `gust-wgpu` enable it for their own tests through a dev-dependency on themselves, so no test command here needs `--features`. The workspace build therefore unifies the feature on, and the off state is observed by the last two steps of the Unit suite, `cargo clippy --locked -p gust -p gust-wgpu --no-default-features --lib -- -D warnings` and `cargo check --locked -p gust -p gust-wgpu --no-default-features --lib` (cargo only: no slangc, no GPU); they are the only steps that build `gust-wgpu` that way. `cargo xtask check-ui` and the `tests/dual` steps of `cargo xtask check-dual` also build `gust` without the feature, as a side effect. A unit test of xtask pins that the manifests set no default feature and no `features` on the `gust` entries of the workspace root and of `gust-wgpu`. Every cargo child that `cargo xtask` starts for the workspace runs under `GUST_PROFILE=dev`, whatever the parent has; a preset other value is logged and overridden. The profile itself is decided in `crates/gust/build.rs` (unit-tested from `cargo test -p gust --lib profile::`): `GUST_PROFILE` is `dev`, `native`, `web` or `cpu`, any other value (an empty one included) fails the build, and a release build with the variable unset is `native` (`web` on `wasm32`) with a warning, so `cargo test --release` outside `cargo xtask` needs `GUST_PROFILE=dev`. A strict profile refuses the `slang-runtime` feature in that script and makes a kernel without an artifact a compile error at the kernel (`gust::profile::require_artifact`). `cpu` (D21, D51) refuses the feature in the same script, and `gust-wgpu` fails to compile under it (`gust::profile::require_gpu_target`); `cargo xtask check-cpu-target` proves both. `cargo xtask check-ui` proves four of the strict-profile cases with the fixtures `profile-native-no-artifact` (E0080 at the kernel line under `native`), `profile-dev-no-artifact` (the same file compiles under `dev`), `profile-unknown` and `profile-empty` (the build script refuses the value) and `profile-native-bridge` (`native` with the feature on is refused); a fixture gets its own variables from an `env.txt`, set after the workspace `dev`, and a `build-error:` line in its `expected.txt` names text of the build script's refusal in cargo's stderr. Switching between plain `cargo` (no `GUST_PROFILE`) and `cargo xtask` (`dev`) rebuilds `gust` and its dependents, because the build script reruns when the variable changes.

Label format: `done (Gpu: NVIDIA GeForce RTX 5090, Vulkan, slangc 2026.20, <commit>)`. The `Cpu` tier is labelled
`done (Cpu: <commit>)`. It is distinct from Unit, whose twin runs under `cfg(test)` (shadow-semantics evidence), and it
is never GPU evidence (D42): a CPU result proves nothing about an adapter.

**Vectors, uniforms and SPIR-V (slices m6.x, m6.x fix round 1).** The examples export SPIR-V, and no example uses a
vector, a matrix or a uniform, so `check-artifacts`, the Spirv suite and `check-full` (the Artifacts and Full modes of
`verify`) also compile the goldens in `tests/fixtures` (`vectors` and `products`; `uniforms`) to SPIR-V into
`<target>/golden-spirv/<area>/` with the pinned `slangc`, `-matrix-layout-column-major` and
`-fvk-use-entrypoint-name`, require exactly the file names pinned in `xtask/src/checks.rs` (`products__run.spv`,
`vectors__run.spv`, `uniforms__run.spv`; a golden that gains a kernel changes the list in the same commit, and the
list is kept apart from `EXPECTED_SPIRV`, which names the examples' files) and run `spirv-val --target-env vulkan1.2` on
each, recorded in the run like the examples' files. That is Spirv-tier evidence for those modules.
`cargo xtask check-feature vectors` and `uniforms` make and validate the same files for one area, then run the GPU
tests of the feature, so its Gpu claim is the RTX 5090 (or whichever adapter) named in the run record.

**Golden sets of M7 (slice m7.x1).** The same step compiles seven more golden sets of `tests/fixtures`: `map`, `grid`,
`workgroup`, `par_for`, `reduce`, `scan` and `compact`, nine sets with the two above (`GOLDEN_SPIRV_SETS` in
`xtask/src/checks.rs`). No example exports the SPIR-V of these kernels, so nothing else covers it. A golden of several
kernels is compiled one section at a time (`shader::golden_sections`). Each set pins its file names, sorted, and a
mismatch fails the run. An entry that does not carry the golden's name keeps its own
name (`map__add_one_map_kernel.spv`), and the names of the `par_for` set hold the hash of the lowered Slang of each
call, so a lowering change that re-hashes a body changes that list in the same commit; the unit tests of xtask
catch a stale list. This is Spirv-tier evidence (the files pass `spirv-val`), not Gpu evidence; the Gpu tests of each
area run through its `check-feature` command.

`cargo xtask spirv-val`, `check-artifacts`, the Spirv suite, `check-full` and the `check-feature` areas that validate
SPIR-V print an informational `OpCopyLogical` count per module, read from `spirv-dis` (a missing `spirv-dis` is said in the line); it is never a failure. Slang emits that
instruction for copies between aggregates of different layouts, and naga's SPIR-V front end refuses it, which is the
whole reason the count exists: GUST's SPIR-V targets Vulkan drivers, and feeding it to naga is unsupported. The
executed route is WGSL. WGSL of the M6 constructs is judged by wgpu's own module creation in the GPU tests (wgpu's
default capabilities), not by a naga run with every capability enabled, which passed WGSL that wgpu refuses. Known
limit: a constant `Mat2` or `Mat3` handed to wgpu as SPIR-V crashes the runner (the faulting layer is not isolated;
SEMANTICS section 4). That is not a statement about the other cases: no M6 GPU case executes SPIR-V, because
`gust-wgpu` is fed WGSL, so every M6 Gpu result is WGSL evidence and the Spirv tier of M6 is `spirv-val` of the
exported modules. Matrix and uniform layout decorations in SPIR-V have never been executed. `cargo xtask slangc` compiles with the same matrix flag
as `gust`: a unit test reads the bodies of `gust`'s `slangc_command` and `slangc_reflection_command` and requires the
flag in each (the whole argument lists of those two are pinned by their own tests in `gust`).

**The naga layout gate (slice mx.n).** `crates/gust-wgpu/tests/naga_layout.rs` parses and validates WGSL with the naga
that wgpu runs (`wgpu::naga`, the lockfile's version; `Capabilities::empty()` for the front end and the validator and
`ValidationFlags::all()`, as `create_shader_module` does, never the all-capabilities default of
`naga::front::wgsl::Options`) and compares the `proc::Layouter` size, alignment and field offsets of every storage and
uniform binding's element type with the descriptor's layout. The WGSL is every compute entry of the 13 goldens of
`tests/fixtures`, compiled by the `slangc` command line (55 modules); every fixture kernel, compiled through the native
reflection helper, which is the route `HeadlessDevice` compiles through (65 modules, 10 of them kernels that no golden
holds); and the committed precompiled WGSL. The test pins those counts, and the golden and fixture `.rs` lists against
the directory. It needs `slangc` on `PATH` and the helper (`GUST_SLANG_REFLECT`) but no adapter, and it fails with a
message naming the missing tool; it does not check a `slangc` version (the CI job `slang` installs the pinned one). It
runs in `cargo xtask check-feature reflection`, in the Slangc suite (the CI job `slang`) and in `cargo test -p
gust-wgpu`, hence in `verify --mode gpu` (the CI job `gpu-software`), where its 9 tests and one result line are counted
in `GPU_SUITE_PIN`; the file takes about 15 s on the Windows development machine. It executes nothing, so it is
WGSL-validity and layout evidence, not Gpu evidence.

**The gust-algo Gpu suite step (slices m7.r1 to m7.r4, D121).** After the `gust-wgpu` call, `verify --mode gpu` and
the Gpu suite run `ALGO_GPU_CALL`, `cargo test --locked -p gust-algo` (`xtask/src/verify.rs`), so the `gpu-software`
job runs it on lavapipe too; the Unit suite does not, which keeps the `unit` job free of wgpu. The tests of the crate
are of two kinds. `twin::`, `schedule::`, `bound::`, `golden::`, `variant::` and `struct_gather::` need no adapter:
the schedule and bound arithmetic, the goldens of the reduce, scan and compact kernels, the v0 CPU twins (and the
twin of the worked struct gather) and the record of which variant ships
(`the_shipped_variants_are_the_measured_ones`). `gpu::` runs the same cases on the first Vulkan adapter, v0 and v1
both, and never skips: with no adapter it fails. Every case has an independent reference (a sequential `f64`
accumulation, an `i128` sum, `Iterator::min`), and the twin and the GPU are each compared with it, never with each
other. Integer sums, `min` and `max` are exact at the schedule boundaries, `sum_wrapping` is exact modulo 2^32, and a
float sum is within the per-level bound of the variant that ran (`gust_algo::bound`). `ALGO_GPU_TESTS` lists the
`tests::gpu::` tests by name and `check_algo_gpu_counts` judges the output of the call: tests ran, none ignored,
every listed test reported `ok`, and the number of `tests::gpu::` tests that passed equals the length of the list, so
a deleted, renamed, ignored or unlisted adapter test fails the step. Adding or removing one changes the list in the
same commit, as for `GPU_SUITE_PIN`. The deepest-schedule cases want a binding of 2^26 + 1 `u32` (256 MiB), which the
portable limits and lavapipe's 128 MiB do not allow: below that limit they say on standard error that the three-pass
reduction did not run, assert the `DeviceLimit` refusal, and run the deepest input that fits (the m7.r4 erratum in
STATUS). The v0 against v1 measurement behind `variant::shipped` (interleaved end-to-end runs on the RTX 5090 and the
Radeon 890M) is not part of the gate; its logs are in the work area and D121 records the outcome.

**The Slang pin (D46, slice m4.r).** `cargo gust` is pinned to the Slang 2026.20 release, and `VALIDATED_BUILDS` ships
empty. The pin was validated on Windows with the release archive itself: every committed artifact set was re-blessed
with that slangc and a helper built against it, the Spirv, Reflect and Gpu suites ran on the RTX 5090, and the three
particle-step SPIR-V modules that changed with the bump were executed on the adapter and read back equal to the
2026.13.1 ones. The Linux archive (`slang-2026.20-linux-x86_64.tar.gz`) and the macOS archive were never executed
before this slice: CI, whose `slang` job installs the pin with the manager, builds the helper with g++, runs the
Slangc tier and re-checks the committed `tests/precompiled` artifacts with `cargo gust check --recompile` (so a pin
bump without a re-bless fails there), and whose gpu-software job does the same on lavapipe, has run the Linux archive:
the `slang` job was green on `af0c2b6`, and its recompile step took 5 s. That run is the evidence for that platform,
and a red run there would have been a finding about the archive, not about the Windows evidence. The macOS archive has
no CI job and stays unexecuted.

**The reflection helper in `cargo xtask` (slice m4.r).** `verify` (the Spirv suite), `check-feature reflection` (the
Reflect suite) and `doctor` use the helper that `GUST_SLANG_REFLECT` names when it is set to a file other than this
checkout's own `target/slang-reflect` output, and build none of their own. Its `--version` Slang tag must equal the pin
in `SLANG_PIN` of `crates/gust/src/toolchain.rs` (and, for `verify`, the output of `slangc -version`); a helper of another build,
such as one built on 2026.13.1, is refused with a message that names both tags. When the variable is unset, the helper
is built from `SLANG_SDK` or `VULKAN_SDK` as before, and the result must carry the pin as well, so an SDK of another
version is refused instead of being used silently (a VulkanSDK that ships 2026.13.1 therefore needs `SLANG_SDK` to
name the managed 2026.20 install). `cargo gust slang build-helper` (which `cargo xtask build-slang-reflect` runs)
keeps a helper only when a build stamp beside it holds the SHA-256 of the packaged C++ source and the helper prints
the Slang tag of the SDK's own `slangc -version`; no file time plays a part (slice m4.z). Any other helper in the
output directory is rebuilt, and the build says why. A helper built before the stamp existed is rebuilt once.
`cargo gust doctor` warns when the first `slangc` on `PATH` is not the pin, naming both versions.
The pin is not enforced on every path. `cargo gust build` and `check --recompile` require the pinned `slangc` and a
helper of the same build; `cargo xtask` checks the helper's tag against the pin, and `verify` requires both
`slangc -version` and the helper's tag to equal the pin. A plain `cargo gust check` compares the helper's tag with the
manifest's and does not run `slangc -version`, so a matching older Slang passes it. `gust::slang`, the run-time bridge
of `dev` builds, checks no version at all (NEXT_TASKS, "M4 follow-ups").
A software Vulkan driver such as lavapipe counts as `Gpu (software)`, never as
hardware evidence. Expected values come from an independent host reference, never from
the shadow bodies (D04). A missing tool or adapter is a failure for its tier, not a skip.

**The additive rule for CPU twins (D26, M3).** A twin assertion adds to the host-reference and GPU assertions of a test
and never replaces either. The twin half needs no adapter, so where it runs alone (`check-cpu`, the `gust::cpu` unit
tests) it is Unit-tier evidence of the shadow semantics; it is never GPU evidence and never the expected value. A test that has a GPU half still compares the GPU readback with
the independent host reference, and the twin is compared with both. A known difference between the twin and the GPU is
a row of the known-mismatch ledger in [SEMANTICS](../SEMANTICS.md) with a measured GPU outcome, not a loosened
assertion, and a difference at an edge case is documented, never chased (D39).

## The Gpu (software) tier (D52)

The workflow `.github/workflows/gpu-software.yml` (job `gpu-software`, `ubuntu-24.04`) runs the Gpu suite on Mesa lavapipe, a software Vulkan implementation, as `cargo --locked xtask verify --mode gpu --record` (the same `cargo test --locked -p gust-wgpu` as the Gpu suite, plus the adapter record). It runs on push to `main`, on pull requests, on `workflow_dispatch` and nightly (`schedule`, 03:00 UTC), and is never a required check: a red run is visible and blocks nothing. The jobs and their lists are in the paragraph that follows the one on what it does not prove. `VK_DRIVER_FILES` points at `lvp_icd.json`, so lavapipe is the only device even if a runner image exposes another driver. Label: `Gpu (software: lavapipe <name as wgpu prints it>, Mesa <version>, Vulkan, slangc <version>, <commit>)`. The workflow uploads `.ai/VALIDATION.json`, the log of the run and the apt and `vulkaninfo` identity as the artifact `gpu-software-<run id>`.

What a green run proves: the Gpu suite's readbacks equal their independent host references on a conforming software Vulkan implementation, with a reproducible driver. The workflow asserts on the record that the adapter is `"device_type": "Cpu"`, that its name contains `llvmpipe`, and that `driver_info` is exactly the pinned string (`MESA_DRIVER_INFO`, Mesa package version and LLVM version); `cargo xtask verify --mode gpu` itself checks the log (slice m5.a2): every `test result:` line must read `ok` with `0 failed; 0 ignored`, the `passed` counts must sum to the pinned number (`GPU_SUITE_PIN.passed` in `xtask/src/verify.rs`) and the number of result lines must equal `GPU_SUITE_PIN.result_lines`; a mismatch fails the mode, names both numbers and is written into the record. Both were measured by the run on the pull request (run 41311817894): 123 passed over 17 result lines (146 over 20 when m5.a2 moved them). Every slice that adds or removes a Gpu test or test file changes them in the same commit, and the doc comment of `GPU_SUITE_PIN` gives the command that recomputes both; drift fails the job by design. The check runs in the Gpu mode on every adapter, so a local `verify --mode gpu` on the RTX 5090 enforces the same numbers. Since m5.f1 `cargo xtask test --suite Gpu` checks the same pin (it makes the same call and prints the same line). The pin is not checked anywhere else: the Fast mode makes the same cargo call, and `check-full` does not make it at all, so a dropped Gpu test file is caught by `verify --mode gpu` or the Gpu suite, never by `check-full` alone (the gates of a slice run both). `cargo xtask status` prints `tier=Gpu (software)` after the usual fields when the record's `device_type` is `Cpu`, so a local record from lavapipe cannot read as hardware.

What it does not prove: anything about a hardware driver (subgroup behaviour, memory model, timing, performance, driver bugs of a vendor), so a `done (Gpu: ...)` label keeps naming a hardware adapter and a software run may be listed beside it, never instead of it. It does not run the Unit job's checks, `check-artifacts` or `check-dual`; `check-examples` and the release-profile ledger are in the nightly list below. A SEMANTICS line stays *measured*, not *proven*, with two adapters listed, and a difference between the two adapters inside the defined domain is a failure to investigate, never a second observation. Edge-case differences stay documented limitations (D39).

Jobs and lists (slice m5.a2, plan M5 R1-10). The workflow has one job, `gpu-software`, and two lists of steps. The pull request list (pull requests, pushes to `main`, and `workflow_dispatch` with `extended` off) is: Mesa from the Ubuntu snapshot with its drift check (apt retries each download five times with a 30-second timeout, and the whole install is tried once more after 60 seconds, because the snapshot service has answered 503 and 504; the snapshot, the packages and the identity checks are unchanged, and there is no fallback mirror); the pinned Slang from the manager (`cargo gust slang install`, then `build-helper`); `cargo gust doctor`; `cargo xtask verify --mode gpu --record` with the pinned test counts; the assertions on the record; `cargo xtask check-difftest --seeds 1-2` (32 generated programs on three parties, interpreter, CPU twin and lavapipe, and the `short_circuit` GPU test; slice m5.c2, below). The nightly list (`schedule` at 03:00 UTC, and `workflow_dispatch` with `extended`, which is the default) is the pull request list plus `cargo xtask check-examples` (the examples' tests with `--include-ignored` and their runs, on lavapipe) and the release-profile mismatch ledger (`cargo xtask check-ledger`: the call and the guard of the second ledger run of the Full mode, so an ignored or renamed ledger test turns the nightly list red), and it runs the differential test on `--seeds 1-72` (1152 programs; the reach of the generator test that every aggregate form is written, m6.d, m6.z1) in place of `--seeds 1-2`. The report is kept in the uploaded artifact as `difftest-report.json`, and a failure names the seed in an annotation. The budget rule is that the pull request list keeps a warm job time of five minutes or less; a step moves from the nightly list to the pull request list (delete its `if:` line) only while the measured warm time stays within it, and STATUS records each list with its measured time. The nightly run has a 40-minute timeout, the others 20. The Slang version lives only in `SLANG_PIN` of `crates/gust/src/toolchain.rs` and the archive hash only in `crates/cargo-gust/src/slang.rs`: a step reads the version from the first and the linux x86_64 hash from the second for the cache key `gpu-software-slang-<os>-<version>-<archive sha256>` (it fails rather than guesses when it cannot), and only the extracted release is cached, because the helper is rebuilt on every run and so cannot outlive a change of its source. `GUST_SLANG_REFLECT` points `xtask` at the manager's helper, and `verify` then builds no second one: it first runs `<helper> --version` and requires its `slang=<tag>` to equal `slangc -version` exactly (a mismatch fails and names both tags). When the variable is unset, names a missing file, or names the default output `<root>/target/slang-reflect/gust-slang-reflect` itself, `verify` builds the helper there as before, so a local run still follows a change of the helper source or of Slang. The job's cargo cache leaves out `target/slang-reflect` and the job removes it, and its Doctor step is `cargo gust doctor`: a helper restored from an old cache was judged up to date by its file times and then could not load the library of another install (run 41346473154; since m4.z freshness is a source-hash stamp, and the cache still leaves the helper out). Moving to a new Slang release (slice m4.r) edits `SLANG_PIN` in `toolchain.rs` and the hash table in `slang.rs`.

Specification assertions fail on every adapter, lavapipe included. A failure caused by the driver is reported, never accepted: it gets an entry under "Known driver failures" (the driver, backend and version from the record, the test by name, the specification text, the observed value, an upstream link if one exists) and the job stays red. Nothing is `#[ignore]`d and no specification assertion is loosened. There is no such entry today.

The mismatch ledger (`crates/gust-wgpu/tests/mismatch.rs`) runs on both kinds of adapter and pins the observations of its unenforced rows once per kind (slice m5.b, D52). `AdapterKind` comes from `adapter_info().device_type` (`Cpu` is software, everything else hardware). A row's `gpu` pin is the hardware observation and `software` is set only where lavapipe differs (18 rows: the NaN bit patterns and `3.0e38 / 3.0e38` of KM-07, and the denormal rows of KM-08; the set-valued KM-09 rows have no per-kind value); the NOTE compares with the running kind's pin, prints `driver`, `backend` and `driver_info`, says "no software pin (the hardware pin accepted m5.b0's value)" for a row without a software pin and fails nothing. Each run writes `ledger-<hardware|software>.txt` under `CARGO_TARGET_TMPDIR` (`target/tmp/` only for the default target directory; debug and release write the same file, and the lines carry no profile), one line per case in the form `LEDGER kind=<kind> driver=<driver> backend=<backend> version=<driver_info> row=<id> what=<text> observed=<summary> status=<ok|note|fail>` (the free-text fields are Rust-quoted), and asserts that the file holds exactly one line per case (132 today). The `gpu-software` workflow uploads them (slice m5.a2): the debug run's file from every run as `debug-ledger-<kind>.txt`, moved aside before the release run overwrites it, and the release run's as `release-ledger-<kind>.txt` from the nightly list. To run it: `GUST_PROFILE=dev cargo test --locked [--release] -p gust-wgpu --test mismatch -- --nocapture`.

Software-tier limitations. The test `an_async_readback_queued_behind_a_busy_kernel_waits_for_the_mapping` (`crates/gust-wgpu/tests/async_readback.rs`) checks that a readback queued behind a slow kernel is still pending on its first poll. On an adapter whose `device_type` is `Cpu` it skips that one coverage assertion and prints why; its value checks still run. Measured on lavapipe (Mesa 25.2.8, CI): 1 poll in each of 3 attempts, about 136 ms each, because the first poll blocks until the kernel has finished. On the RTX 5090 the assertion runs and passes (27 polls in one attempt). So a green `gpu-software` run does not prove the pending path of the async readback; only a hardware run does (D52).

Mesa is pinned two ways (plan M5, R1-11, made stricter). The install step uses the Ubuntu snapshot service as its only apt source: one deb822 source, `URIs: https://snapshot.ubuntu.com/ubuntu/<SNAPSHOT_ID>/` with the Ubuntu archive keyring, with the runner's own sources and lists left out of that install, so no package of it floats to the live archive. R1-11 allowed the runner's mirror with a `Snapshot:` field, which a run showed fetching the live archive beside the snapshot. The package is installed as `mesa-vulkan-drivers=<MESA_VERSION>`, and a drift step fails the job unless `apt-cache policy` reports exactly that version installed; the record's `driver_info` must equal `MESA_DRIVER_INFO` exactly. The versions of the Mesa package, `libllvm20`, `spirv-tools`, `vulkan-tools` and `libvulkan1` are written to `environment.txt` in the artifact. A new Mesa is a deliberate commit that edits `SNAPSHOT_ID`, `MESA_VERSION` and `MESA_DRIVER_INFO`. If the snapshot service cannot be used, the fallbacks are the tagged `gfx-rs/ci-build` archive pinned by SHA-256, and as a recorded deviation only, floating apt with the drift check. Slang comes from the manager (`cargo gust slang install`, as the paragraph on jobs and lists above says). The first cold run on a hosted runner took 1 minute 52 seconds (run 41311817894); the first warm run, with both caches restored, took 1 minute 27 seconds by its log timestamps (run 41313704836).

## The differential batch (slice m5.c2, plan M5 R1-13)

`cargo xtask check-difftest [--seeds <list|range|random:N>] [--cpu-only] [--report PATH]` runs the generator, the
interpreter, the CPU twin and (without `--cpu-only`) the GPU on generated scalar kernels, through `difftest-run` of
`tests/difftest` ([DIFFTEST](DIFFTEST.md)). It does not reimplement the harness: it runs it, reads the `report.json` by
fields and fails unless the report has the requested mode and seeds, `programs_executed` equal to 16 times the seeds
(so a run that silently executed fewer programs fails and the message names both numbers), no mismatch (each is named
with its seed, program and kind), and, without `--cpu-only`, an adapter. Without `--cpu-only` it also runs the harness
crate's `short_circuit` test with `--ignored`, which the plain `cargo test` of that crate leaves out: the GPU must not
evaluate a right operand of `&&`/`||` that the left operand makes unnecessary (the WGSL that Slang emits is read for
it). The default is the 8 seeds of `tests/difftest/seeds.txt` (128 programs). `random:N` draws N seeds from the clock,
prints them and runs them as a list, so a failure is reproduced by naming that list.

| Where it runs | Command | Tier a pass reaches | Programs |
| --- | --- | --- | --- |
| Unit suite (and so the Slangc suite), CI job `difftest` (the `unit` and `slang` jobs pass `--skip-difftest`) | `cargo xtask check-difftest --cpu-only --seeds 1-4`, after the format check, clippy and tests of `tests/difftest` | Unit (interpreter against CPU twin; shadow-semantics evidence, never GPU evidence) | 64 |
| Gpu suite, last step | `cargo xtask check-difftest` | Gpu (the adapter the report names) | 128, and the `short_circuit` GPU test |
| `check-full`, after `check-precompiled` and `check-web` | the same, in process | Gpu (hardware, on the adapter that run records) | 128, and the `short_circuit` GPU test |
| `gpu-software`, pull request list | `cargo xtask check-difftest --seeds 1-2 --report <artifact directory>` | Gpu (software), lavapipe | 32, and the `short_circuit` GPU test |
| `gpu-software`, nightly list | `cargo xtask check-difftest --seeds 1-72 --report <artifact directory>` | Gpu (software), lavapipe | 1152, and the `short_circuit` GPU test |

What a pass proves: for the generated programs of those seeds, which are in-domain kernels over scalar `u32`, `i32`,
`bool` and `f32` buffers (with vector and matrix locals since DIFFTEST_FORMAT 6) of the operator set of DIFFTEST
(R1-4), the GPU output equals the interpreter's output (integers and booleans exactly, floats inside the interval
the interpreter derived), the CPU twin equals it bit for bit, and the harness executed every planned program. What
it does not prove: anything about programs outside the generator's space (no loops over runtime bounds, no atomics,
no structs, no vector or matrix buffers or results, and none of the vector and matrix forms DIFFTEST lists as
never written by the seeds run), anything about a seed that was not run, anything about
another driver than the one named in the report, or, for the `--cpu-only` run, anything about a GPU at all. The Unit
run cannot see a Slang or driver fault; a program the interpreter rejects is discarded and counted in the report, not
run. That includes the programs discarded as `static` (a constant the shader compilers may refuse at shader-creation
time): the corpus keeps none, so the batch says nothing about what the compilers do with them. Since DIFFTEST_FORMAT 5
a non-literal divisor goes through `__gust_div`/`__gust_rem`, which slangc does not fold (D77), so a zero divisor in a
dead branch no longer fails with E30002; a literal zero divisor is E0317, and the remaining limits are in
[DIAGNOSTICS](../DIAGNOSTICS.md). A harness failure (exit 2: a build error, a stale template lockfile, a result
file missing) fails the command as well and is never reported as a pass; a report left by an earlier run cannot pass the next one (the file is removed
first). Measured costs are in DIFFTEST, "Gates".

## What each scan sees

`cargo xtask lint` reads **tracked files only** (`git ls-files`). `cargo xtask docs-check` and `cargo xtask check-arch` read tracked files **plus untracked files that are not ignored** (the files the next commit would contain). A new script, or a new file with a machine-specific path, is therefore not caught by `lint` until it is staged with `git add`, while a broken link or a stray `ir` module is caught before that. Ignored files (`target/`, `generated-wgpu/`, `.ai/VALIDATION.json`) are scanned by none of them.

## Minimum Rust version

The workspace declares `rust-version = "1.90"` (D30, which supersedes the 1.88 in D29: the locked `ordered-float 5.5.0`, pulled in by wgpu-hal, declares 1.90). The CI job `msrv` measures the claim: it installs exactly Rust 1.90.0 and runs `cargo check --workspace --all-targets --locked` (all targets, so test code is covered). It needs no slangc and no GPU and runs no tests, so it is Unit-tier evidence of compilation only. It is not a required check yet. A local run needs a 1.90 toolchain: `rustup toolchain install 1.90.0`, then `RUSTUP_TOOLCHAIN=1.90.0 cargo check --workspace --all-targets --locked`. `cargo xtask check-full` uses the stable toolchain and does not measure the minimum version; `.ai/VALIDATION.json` lists it under `untested`.

## Record policy

Routine checks do not rewrite `.ai/VALIDATION.json`. Use `cargo xtask verify --mode <mode> --record` only when a durable record for a non-full mode is useful. `cargo xtask check-full` records by default and is the release-evidence path. The record carries `git_commit` (the output of `git rev-parse HEAD`, taken before the checks start) and `git_dirty` (true when `git status --porcelain --untracked-files=all` listed anything: modified, staged, or untracked files that are not ignored, whatever `status.showUntrackedFiles` says). Both are `null` when git is unavailable or refuses the repository. A record with `git_dirty: true` is evidence about that working tree, not about the commit. `cargo xtask status` prints them as `commit=` and `dirty=`; a record written before the stamp existed prints `unknown`. The record also carries `adapter` (m4.h): the Vulkan adapter that `HeadlessDevice::new()` selects in the example process, which uses the same selection logic as the GPU steps (it is a separate process, so the record does not prove that every later step ran on that adapter if the machine changes in between). It is read from the one JSON line that `cargo run --locked --quiet -p gust-wgpu --example adapter_info` prints (`HeadlessDevice::adapter_info()`: `name`, `vendor`, `device`, `device_type`, `backend`, `driver`, `driver_info`; no path, and the usual redaction applies). Any Vulkan adapter satisfies the GPU tiers, a software one (lavapipe) included, so `device_type` (`Cpu` for a software adapter) says which ran. Every verify mode runs this step before its first GPU step: a failed run, an empty output, a second line, or a blank name, device type or backend fails the mode and the record then says `"adapter": null`. A record written before m4.h has no `adapter` member. It also carries `skipped_checks` (m4.i): the checks that `check-full --skip-web` was asked to leave out (`["check-web"]`), an empty list for a run that skipped nothing; a record written before m4.i has no such member, and `untested` still lists `browser WebGPU` there.

## Required evidence by boundary

- Validator: accepted fixture or single-cause rejection test with a meaningful diagnostic.
- Lowering: reviewed Slang golden plus a source-structure assertion when useful.
- Shader target: WGSL compile smoke in routine tests; SPIR-V validation in artifact/full checks.
- Runtime: real GPU readback against an independent host reference, including partial and multiple workgroups.
- Engine proof: explicit contract first, exact transfer/residency/count assertions, no silent fallback.

## What not to do

- Do not run `cargo xtask check-full` as the first check for a local compiler edit.
- Do not auto-bless goldens without reviewing the semantic diff.
- Do not treat `spirv::validate_structure` as semantic SPIR-V validation; external `spirv-val` owns that layer.
- Do not introduce shared `HeadlessDevice` fixtures until `cargo xtask measure-tests` isolates adapter/device setup as the bottleneck.
- Do not commit regenerated `generated-wgpu/` outputs; full/artifact checks regenerate
	them locally and validate the SPIR-V files before leaving them ignored. The Artifacts and Full modes
	(`check-artifacts`, `check-full`, the Spirv suite) empty `generated-wgpu/` before the examples export
	into it (m4.h), so the file of a deleted or renamed kernel cannot satisfy the name check or pass
	`spirv-val`; the other modes leave the directory alone.
