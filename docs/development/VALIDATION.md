# Validation strategy

Validation is layered. Choose the cheapest command that can falsify the current claim, then widen only when the touched boundary requires it.

## Command tiers

| Situation | First check | Wider check | Release check |
| --- | --- | --- | --- |
| Validator/lowering/golden change | `cargo xtask check-feature macro` | `cargo xtask check-workspace` | `cargo xtask check-full` |
| Reflection/layout change | `cargo xtask check-feature reflection` | `cargo xtask check-feature gpu-runtime` | `cargo xtask check-full` |
| Semantics contract change (SEMANTICS.md, a ledger row, twin behaviour, `gust::cpu`) | `cargo xtask check-cpu` and `cargo test --locked -p gust --lib cpu` | `cargo xtask check-feature gpu-semantics` (it runs the ledger test `mismatch`) and `cargo xtask check-dual --check-only` | `cargo xtask check-full` (adds the release ledger run and `check-dual` in full mode) |
| Loop dialect change | `cargo xtask check-feature loops` | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Result lowering/match | `cargo xtask check-feature result` | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Diagnostic sidecar maps | `cargo xtask check-feature core` | `cargo xtask check-workspace` | `cargo xtask check-full` |
| wgpu runtime/cache/buffer change | `cargo xtask check-feature gpu-smoke` or `gpu-runtime` | `cargo xtask check-feature wgpu` | `cargo xtask check-full` |
| GPU semantic feature | focused macro/golden test + one GPU feature test | `cargo xtask check-feature gpu-semantics` | `cargo xtask check-full` |
| Example-only change | `cargo test -p <example> -- --include-ignored` | `cargo xtask check-examples` | `cargo xtask check-full` |
| Artifact/export change | relevant example binary | `cargo xtask check-artifacts` | `cargo xtask check-full` |
| Unknown dirty tree | `cargo xtask check-changed` | command it selects | `cargo xtask check-full` if release evidence is needed |

## Evidence tiers

Every status line, task report, and decision that cites evidence names the highest
tier it reached. A tier is claimed only with a run record (command, result, and for
Gpu the device).

| Tier | Claim | Typical command |
| --- | --- | --- |
| Unit | Macro validation, translation, and xtask logic pass without external tools; the declared minimum Rust version compiles every workspace target | `cargo test -p gust-macros`, `cargo test -p xtask`, `cargo xtask lint` (CI), `cargo xtask check-ui`, `cargo xtask check-cpu`, `cargo test --locked -p gust --lib cpu::tests::`, `cargo test --locked -p gust --lib artifact::tests::`, `cargo test --locked -p gust --test artifact`, `cargo xtask check-dual --check-only` (a separate step of the CI `unit` job, not of the Unit suite), CI job `msrv` |
| Slangc | The generated Slang compiles to the target | WGSL compile smoke tests, `cargo xtask check-fast` |
| Spirv | Exported SPIR-V passes `spirv-val --target-env vulkan1.2` | `cargo xtask check-artifacts`, `cargo xtask spirv-val <file.spv> --target-env vulkan1.2` |
| Reflect | The D17 layout gate matches the descriptor | `cargo xtask check-feature reflection` |
| Gpu | Readback on a device equals an independent host reference | GPU tests, `cargo xtask check-full` |

Each tier is one command: `cargo xtask test --suite <Tier>`. Unit runs `cargo test --locked -p gust-macros`, `cargo test --locked -p xtask`, lint, docs-check, check-arch, check-ui, check-cpu, `cargo test --locked -p gust --lib cpu::tests::` (the `gust::cpu` unit tests; no slangc, no GPU), `cargo test --locked -p gust --lib artifact::tests::` and `cargo test --locked -p gust --test artifact` (`verify_artifact` on the committed precompiled fixture; no slangc, no GPU). Slangc is Unit plus `cargo test --locked -p gust --lib` and `cargo test --locked -p gust --test diagnostics` (the Rust-line annotation of real Slang failures). Spirv is `check-artifacts`, Reflect is `check-feature reflection`, Gpu is `cargo test --locked -p gust-wgpu` (a missing adapter fails), and Full is `check-full`, which also runs `cargo test --locked --release -p gust --lib -- slang cpu::tests::invocations_are_capped_at_the_id_range_in_release` so that the release-only (`cfg(not(debug_assertions))`) tests run (the source-map fallback and the `gust::cpu` id-range cap, each required `ok` by name), and `cargo test --locked --release -p gust-wgpu --test mismatch` so that the known-mismatch ledger (`docs/SEMANTICS.md`) also runs with `overflow-checks` off (the Gpu suite runs it with checks on). A suite prints what it does not cover, and a pass of one tier says nothing about the tiers above it.

Label format: `done (Gpu: NVIDIA GeForce RTX 5090, Vulkan, slangc 2026.13.1, <commit>)`.
A software Vulkan driver such as lavapipe counts as `Gpu (software)`, never as
hardware evidence. Expected values come from an independent host reference, never from
the shadow bodies (D04). A missing tool or adapter is a failure for its tier, not a skip.

**The additive rule for CPU twins (D26, M3).** A twin assertion adds to the host-reference and GPU assertions of a test
and never replaces either. The twin half needs no adapter, so where it runs alone (`check-cpu`, the `gust::cpu` unit
tests) it is Unit-tier evidence of the shadow semantics; it is never GPU evidence and never the expected value. A test that has a GPU half still compares the GPU readback with
the independent host reference, and the twin is compared with both. A known difference between the twin and the GPU is
a row of the known-mismatch ledger in [SEMANTICS](../SEMANTICS.md) with a measured GPU outcome, not a loosened
assertion, and a difference at an edge case is documented, never chased (D39).

## Single-stage commands

Workflow commands live in `cargo xtask` (D27); no shell or PowerShell scripts are tracked.

| Command | Use |
| --- | --- |
| `cargo xtask lint` | No tracked `.ps1`, `.psm1`, `.psd1`, `.bat`, `.cmd` or `.sh` file, and no machine-specific path in tracked text. Machine paths include Windows, Unix and WSL home spellings (a Unix home name must be followed by `/`, a quote or the end of the line); two test files may spell placeholder names only. Non-UTF-8 and binary files are skipped, and the summary counts them. Scans tracked files only (`git ls-files`): a new file is not linted until `git add` has staged it (see "What each scan sees" below). Also runs in `verify --mode smoke`, `check-fast`, `check-full` and CI. |
| `cargo xtask docs-check` | Relative Markdown links in project `.md` files (any case of the extension; tracked files plus untracked files that are not ignored; footnote definitions are not links) resolve to project files (anchors, query strings and external links are not checked), no merge-conflict markers in text files, and `docs/DECISIONS.md` ids are unique (also when the repeat is not adjacent) and increasing with the right "Next id". Sees untracked files that are not ignored, unlike `lint`. Same runs as `lint`. |
| `cargo xtask check-arch` | D02 guardrails: per-crate dependency allow-list (`gust-macros` = proc-macro2, quote, syn; `gust` = gust-macros; `gust-wgpu` = gust, pollster, wgpu; `xtask` = none), read from `cargo metadata --format-version 1 --locked --no-deps` so that cargo itself resolves `workspace = true`, `package` renames, target tables and every dependency kind (normal, dev, build). Each dependency is judged by its real package name; an allow-listed one must not be renamed with `package`, use a git source or an alternative registry, or be a path dependency outside `crates/<name>` (a workspace crate must be exactly `crates/<name>`). A manifest cargo rejects, for example an inherited dependency with no `[workspace.dependencies]` entry, fails the check with cargo's own message. The metadata is parsed by a small std-only JSON reader in xtask; no dependency is added. `cargo metadata --no-deps` shows declared sources only, so a root `[patch.crates-io]` or `[replace]` redirect is caught in `Cargo.lock` instead: every locked package named in an allow-list must resolve from crates.io (a redirect to git or to a local path changes the lockfile's `source`), and every workspace crate must be a path package. The lockfile is read by a std-only line reader (no network, no full dependency resolve, which would download manifests for every platform); it is trusted as written because the suites' cargo calls use `--locked` and fail on a stale lockfile. Not checked: transitive dependencies outside the allow-lists, and `[workspace.dependencies]` entries that no checked crate inherits. Also: no `ir`, `*_ir` or `ir/` module or file under `crates/` outside a `future/` path, no SPIR-V library in the compiler crates. A change is a DECISIONS entry plus an edit of `xtask/src/arch.rs`. Needs git and cargo. Sees untracked files that are not ignored, unlike `lint`. Same runs as `lint`. |
| `cargo xtask check-ui` | Compile-fail checks for the wording of `#[diagnostic::on_unimplemented]` on `GpuPod`, `Kernel` and `Run`, and for the errors of typed calls and const layout assertions (see "Runtime, typed-call and diagnostic test targets"). For each fixture crate under `tests/ui/` it runs `cargo check --locked --color never --manifest-path tests/ui/Cargo.toml -p <crate> --message-format json` and reads cargo's JSON diagnostics from stdout. A crate with an `expected.txt` (`key: value` lines, `#` comments) must fail with exactly one error-level message of the crate itself (`target.name` is the crate; warnings, the summary note and other crates' diagnostics are ignored, and a second error is a problem that names it), and that error must satisfy every key. Three keys are required, appear once and match exactly: `code` (`code.code`; `code: none` instead requires `"code": null`, which is what a macro's own `compile_error!` has, and is accepted only with at least one `message:` since the text is then all that names the error), `file` (a primary span's `file_name`, relative to `tests/ui`, backslashes read as slashes) and `line` (that span's `line_start`; one span must carry both). A primary span outside the crate's own directory, such as core's `panic.rs` for a `const` panic that a macro generated, is reported at the outermost of its macro call sites (`expansion.span`, recursively) that lies in the crate's directory, so `file` and `line` name the user's `#[gust::gpu]` line there; with no such call site it is reported where it is and cannot match, and `label` is still read from the primary span itself. `message` (any number) is a substring of the error's `message` or of a child message, where the attribute's `note` lands. `label` (any number) is a substring of the label of that same primary span, where the attribute's `label` lands. Unknown keys, repeated single-valued keys, a missing required key and absolute paths are errors. A crate without one must compile, which guards valid code against the attribute. Only the listed keys are compared, not the whole rustc output, so toolchain wording changes elsewhere do not break it. `tests/ui` is a workspace root of its own with its own committed `Cargo.lock` (`--locked` fails loudly when it drifts); it is not a member of the root workspace, so `cargo test --workspace` never builds it. Needs cargo only (no slangc, no GPU); its only dependencies are `gust` and `gust-macros` (and their proc-macro crates). Part of the Unit suite and of `verify` smoke, fast and full modes (`check-fast`, `check-full`). Without `CARGO_TARGET_DIR` it builds under `tests/ui/target` (ignored). |
| `cargo xtask check-cpu` | The CPU-twin evidence, with no slangc and no GPU: `cargo test --locked -p <example>` for vector-add, polynomial, signal-pipeline, particle-step, typed-pipeline, atomic-counter, staged-graph and component-pool, whose non-ignored tests (each call must report at least one passed test: the test-count guard) (the `twin_*` tests, the twin's buffer-aliasing check and polynomial's size guard) run each kernel's macro-emitted CPU twin against its host reference. The twin tests (and the derivation-domain guard of the examples that have one) are also required by name: each must be reported `ok`, so a deleted, renamed or `#[ignore]`d one fails the step even when its siblings pass (`CPU_REQUIRED_TESTS` in `xtask/src/checks.rs`, pinned against the example sources by a unit test). The GPU comparison of the same twins stays in the ignored example tests of `check-examples`. Later slices append their examples to the list (`CPU_TESTS` in `xtask/src/checks.rs`; a unit test requires `--locked` on each call). A step of the Unit suite (and so of Slangc); CI runs it through its Unit step. Not part of `check-fast`. Budget (plan R5): if it adds more than five minutes to the CI unit job it is narrowed, never dropped. |
| `cargo xtask check-dual [--check-only]` | Cross-crate evidence that the CPU twin exists only in dual builds. It refuses when `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS` or `CARGO_BUILD_RUSTFLAGS` is present (even empty), notes a `CARGO_TARGET_<TRIPLE>_RUSTFLAGS` (replaced, not extended), and runs, all `--locked` with `--target-dir <target>/dual`: `cargo fmt --check` of `tests/dual`; `cargo build --workspace --all-targets` with `CARGO_ENCODED_RUSTFLAGS` set to `--cfg` and `gust_dual` joined by 0x1f; clippy `-D warnings` with the cfg on `tests/dual` and on vector-add and polynomial (`--all-targets`, so the code behind `cfg(gust_dual)` is linted); E1 `cargo test --manifest-path tests/dual/Cargo.toml -p consumer --lib --no-run` without the cfg (exactly one E0277 on target `consumer`); E2 the same with the cfg, then run (all four consumer tests reported ok by name, including `overflow_mode_is_the_dependents_own`, which shows `gust::cpu::overflow_checks!()` reports the calling crate's per-package overflow mode, and the two `twin_overflow` tests, which dispatch an integer kernel with `u32::MAX + 1`: the twin of `kernel-lib`'s kernel follows `kernel-lib`'s overflow mode and the twin of the consumer's own kernel follows the consumer's); E3 `cargo check ... -p consumer --bin prod` without the cfg (exactly one E0277 on target `prod`). Without it (needs a Vulkan GPU) it then runs `cargo run --locked -p vector-add` and `-p polynomial` with the cfg, each of which must print exactly one `CPU twin: matches (N elements, max ULP k)` line with N above 0 (polynomial also a labelled debug-profile, single-threaded wall time), and `cargo run --locked -p vector-add` without the cfg, which must print no `CPU twin` line. `check-full` runs the full mode. The separate target directory keeps the main cache warm (S3: a no-change workspace build afterwards compiles nothing); it is about 6 to 8 GB. |
| `cargo xtask bless` | Reruns the Slang golden tests (`cargo test --locked -p gust-macros golden`) with `BLESS_GOLDEN=1`: a golden whose emitted text differs is rewritten, its line diff printed and its test failed with "golden blessed; review the diff and rerun without BLESS_GOLDEN". Then lists changed fixtures with `git diff --stat`. Exits 0 only when no fixture changed. Review every diff before committing. |
| `cargo xtask test --suite Unit\|Slangc\|Spirv\|Reflect\|Gpu\|Full` | One evidence tier as one command (below). Each suite prints its tier and what it does not cover; a missing tool or adapter fails the suite. |
| `cargo xtask doctor` | Tool readiness. Exits non-zero when cargo, rustc, slangc or the reflection helper is missing; `spirv-val` is reported and required only for artifact and full modes. |
| `cargo xtask doctor --smoke` | Doctor, then the hand-written `vector-add.slang` toolchain fixture compiled to WGSL and SPIR-V in a fresh directory under the cargo target directory, and the SPIR-V validated. ## What each scan sees

`cargo xtask lint` reads **tracked files only** (`git ls-files`). `cargo xtask docs-check` and `cargo xtask check-arch` read tracked files **plus untracked files that are not ignored** (the files the next commit would contain). A new script, or a new file with a machine-specific path, is therefore not caught by `lint` until it is staged with `git add`, while a broken link or a stray `ir` module is caught before that. Ignored files (`target/`, `generated-wgpu/`, `.ai/VALIDATION.json`) are scanned by none of them.

## Minimum Rust version

The workspace declares `rust-version = "1.90"` (D30, which supersedes the 1.88 in D29: the locked `ordered-float 5.5.0`, pulled in by wgpu-hal, declares 1.90). The CI job `msrv` measures the claim: it installs exactly Rust 1.90.0 and runs `cargo check --workspace --all-targets --locked` (all targets, so test code is covered). It needs no slangc and no GPU and runs no tests, so it is Unit-tier evidence of compilation only. It is not a required check yet. A local run needs a 1.90 toolchain: `rustup toolchain install 1.90.0`, then `RUSTUP_TOOLCHAIN=1.90.0 cargo check --workspace --all-targets --locked`. `cargo xtask check-full` uses the stable toolchain and does not measure the minimum version; `.ai/VALIDATION.json` lists it under `untested`.

## Record policy

Routine checks do not rewrite `.ai/VALIDATION.json`. Use `cargo xtask verify --mode <mode> --record` only when a durable record for a non-full mode is useful. `cargo xtask check-full` records by default and is the release-evidence path. The record carries `git_commit` (the output of `git rev-parse HEAD`, taken before the checks start) and `git_dirty` (true when `git status --porcelain --untracked-files=all` listed anything: modified, staged, or untracked files that are not ignored, whatever `status.showUntrackedFiles` says). Both are `null` when git is unavailable or refuses the repository. A record with `git_dirty: true` is evidence about that working tree, not about the commit. `cargo xtask status` prints them as `commit=` and `dirty=`; a record written before the stamp existed prints `unknown`. The record also carries `adapter` (m4.h): the Vulkan adapter that `HeadlessDevice::new()` selects in the example process, which uses the same selection logic as the GPU steps (it is a separate process, so the record does not prove that every later step ran on that adapter if the machine changes in between). It is read from the one JSON line that `cargo run --locked --quiet -p gust-wgpu --example adapter_info` prints (`HeadlessDevice::adapter_info()`: `name`, `vendor`, `device`, `device_type`, `backend`, `driver`, `driver_info`; no path, and the usual redaction applies). Any Vulkan adapter satisfies the GPU tiers, a software one (lavapipe) included, so `device_type` (`Cpu` for a software adapter) says which ran. Every verify mode runs this step before its first GPU step: a failed run, an empty output, a second line, or a blank name, device type or backend fails the mode and the record then says `"adapter": null`. A record written before m4.h has no `adapter` member.

## Required evidence by boundary

- Validator: accepted fixture or single-cause rejection test with a meaningful diagnostic.
- Lowering: reviewed Slang golden plus a source-structure assertion when useful.
- Shader target: WGSL compile smoke in routine tests; SPIR-V validation in artifact/full checks.
- Runtime: real GPU readback against an independent host reference, including partial and multiple workgroups.
- Engine proof: explicit contract first, exact transfer/residency/count assertions, no silent fallback.

## What not to do

- Do not run `cargo xtask check-full` as the first check for a local compiler edit.
- Do not auto-bless goldens without reviewing the semantic diff.
- Do not treat `spirv::validate_structure` as semantic SPIR-V validation; external `spirv-val` owns that layer.
- Do not introduce shared `HeadlessDevice` fixtures until `cargo xtask measure-tests` isolates adapter/device setup as the bottleneck.
- Do not commit regenerated `generated-wgpu/` outputs; full/artifact checks regenerate
	them locally and validate the SPIR-V files before leaving them ignored. The Artifacts and Full modes
	(`check-artifacts`, `check-full`, the Spirv suite) empty `generated-wgpu/` before the examples export
	into it (m4.h), so the file of a deleted or renamed kernel cannot satisfy the name check or pass
	`spirv-val`; the other modes leave the directory alone.
